# Stage58 — доказанная MMU-карта и закрытие CEVA-сеанса

## Результат

Восстановлено происхождение `pointer | 0x10000000`, которое на Stage57 было
только гипотезой. Все пять предоставленных вариантов RedBoot содержат
побайтно одинаковую 17 408-байтовую таблицу с SHA-256
`80a4560940f1313613a249ed01bce202961ad6ceeaa9809f3aa034f6d334e45b`.
Две семьи кода RedBoot независимо загружают её физический адрес `0x00060000`
в TTBR. Exact-аудит проверяет 14 вызовов и 12 слов MMI, оба семейства кода и
все пять копий таблицы. Ничего на консоли и в MMIO не запускалось.

## Карта памяти RedBoot

| Virtual address | Physical address | Атрибут |
|---|---|---|
| `00000000–000FFFFF` | тот же диапазон | L2: первые 64 КиБ uncached, дальше cached |
| `00100000–0FFFFFFF` | identity | cached + buffered |
| `10000000–1FFFFFFF` | `00000000–0FFFFFFF` | uncached + unbuffered |
| `2E000000–2FFFFFFF` | identity | uncached + unbuffered |
| `90000000–9FFFFFFF` | identity | uncached + unbuffered |
| `D0000000–FFFFFFFF` | identity | cached + buffered |

Остальные L1-зоны в этой таблице являются fault descriptors. Поэтому для
физической RAM ниже `0x10000000` выражение `PA | 0x10000000` выбирает ту же
память через некэшируемое и небуферизованное окно. Это теперь свойство точной
таблицы, а не догадка по использованию адресов. Оно не разрешает применять OR
к адресам вне покрытого диапазона.

RedBoot семейства 1/2/4 устанавливает TTBR в `0x0003D1E4`, семейства 3/5 — в
`0x0003B4D8`. Обе функции отключают MMU, инвалидируют cache/TLB, записывают
TTBR `0x00060000` и DACR `1`. MMI при reset меняет CP15 control и пользуется
уже установленной RedBoot таблицей; новой таблицы в найденном пути нет.
Это не определяет, какой из пяти RedBoot находится на конкретной консоли.

## Жизненный цикл CEVA

Глобальное слово `0x0055B7A8` — счётчик активного CEVA core, а не простой
boolean. Start wrapper при нуле инициализирует PIU, запускает core и увеличивает
счётчик; при ненулевом значении этот wrapper сразу возвращает успех.

Обычная остановка `0x00349300`:

1. при значении `1` посылает mailbox-команду `0x84`;
2. очищает bit `0x100` в `0x90530468`;
3. выполняет два clock/power вызова;
4. уменьшает счётчик.

Force path `0x003493FC` уменьшает счётчик в цикле, но close/power выполняет
только на переходе `1 → 0`. Ни один из этих путей не удаляет созданные PIU
thread/IRQ objects: транспорт живёт дольше отдельного codec-сеанса.

Команды C0/C1/C2 после mailbox reply копируют по `0x60` байт через доказанное
uncached-окно. OEM при нулевом reply способен уйти в бесконечный цикл. Новый
provider не должен воспроизводить это: все ожидания остаются конечными.

## Изменение чистой C-модели

В `codec_lab` добавлен `spmp_ceva_cleanup_allocations`. Он работает только в
`STOPPING`, вызывает предоставленный release callback не более 16 раз и
снимает запись с учёта только после успешного callback. Если callback вернул
ошибку, указатель и размер остаются outstanding; повторный вызов продолжает
очистку. Переход `COMPLETE_STOP` по-прежнему запрещён до нулевого счётчика
выделений.

Это защитная политика SPMP-OS, а не утверждение, что OEM сам очищает утечки.
Модель не обращается к MMIO; CI настроен собирать её также как ARMv5TE
soft-float object. В текущей рабочей среде ARM-компилятор отсутствует, поэтому
локально выполнены C11 host-тесты, а ARM-сборка должна подтвердиться CI.
