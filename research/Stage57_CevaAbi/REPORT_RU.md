## Ready и boot

| Стадия | Регистр | Значение | OEM-строка |
|---|---:|---:|---|
| CEVA ready | `0x9053200C` | `0x43585244` | `CEVA is ready` |
| codec booted | `0x90532044` | `0x43584254` | `CEVA is booted` |

Константы соответствуют source-style multi-character literals `'CXRD'` и
`'CXBT'`. Это имена состояний, а не четыре байта текста в порядке памяти.

Обе wait-функции сначала читают регистр, затем вызывают OEM delay `(10, 0)` и
только после этого сравнивают значение. Аргумент `N` даёт максимум `N+1`
чтений. Media loader передаёт 30, следовательно фактический предел — 31
чтение/задержка. При timeout вызывается reset/diagnostic path; debug flags
`0x01000000` или `0x02000000` превращают ошибку в бесконечный цикл. Новый код
не должен повторять это поведение.

## Входящий PIU-пакет и переполнение OEM

```text
+0  u8   opcode
+1  u8   no_reply
+2  u16  payload_bytes, little endian
+4       payload
```

`dspCmdDispatcher` копирует заголовок и затем ровно `payload_bytes` из
`0x90532040 | 0x10000000`. Целевой буфер начинается в `0x00640C60`, следующий
eCos/IRQ-объект — в `0x00640D60`: доступно ровно 256 байт, то есть payload не
может превышать 252 байта.

В оригинале проверки этого ограничения нет. Повреждённый или враждебный CEVA
пакет может перезаписать соседнее состояние RTOS. Публичный auditor содержит
безопасный validator и тестирует границы 252/253. Будущий provider обязан
отклонять oversized-пакет до копирования.

## Opcode 0x40: LCD geometry

Минимально наблюдаемая структура запроса имеет 36 байт целиком:

| Абсолютное смещение | Поле |
|---:|---|
| `+4` | requested width, `u32` |
| `+8` | requested height, `u32` |
| `+0x20` | LCD format/mode enum, точное публичное имя пока неизвестно |

Ширина и высота ограничиваются `min(requested, active LCD dimension)`. При
изменении кэшированных значений оригинал выполняет последовательность:

1. отключить display path 0;
2. перестроить display path;
3. применить format/mode;
4. включить display path 0.

Это подтверждает, что CEVA способен запрашивать перестройку вывода, но не даёт
SPMP-OS права вызывать найденные функции без восстановления их lock/thread
контракта. Opcode `0x42` отдельно вызывает штатный `lcd_init2`.

## Opcode 0x41: scale engine

Запрос занимает минимум 52 байта целиком и содержит 12 слов payload. Из них
восстановлено преобразование в локальный 60-байтовый descriptor:

| Request | Descriptor | Использование |
|---:|---:|---|
| `+4/+8` | `+0x1C/+0x1E` | width/height, ограниченные активным LCD |
| `+4/+8` | rect `+0x28/+0x2A` | исходные width/height; x/y равны нулю |
| `+0x14` low16 | `+4` | 16-битное поле |
| `+0x1C` | `+0x18` | слово descriptor |
| `+0x20/+0x24/+0x28` | `+8/+0xC/+0x10` | три слова descriptor |
| `+0x2C` | `+0x20` | слово descriptor |
| constant | `+0` | mode 9 |
| `+0x30` | — | выполнить до ответа, если nonzero; иначе после ответа |

Поля `+0x0C`, `+0x10` и `+0x18` передаются через ABI helper, но в этой версии
helper их не использует. Это не означает, что их можно удалять из wire ABI.
Scale backend работает с MMIO `0x92007000/0x92007028`; переносить эти обращения
в новый код до проверки платы нельзя.

## Opcode 0x43/0x44: память

CEVA может попросить ARM выделить размер из request `+4`. Opcode `0x43`
вызывает обычный OEM allocator через общий heap control pointer `0x00514250` и
возвращает raw ARM pointer в response `+4`. Opcode `0x44` освобождает указатель
тем же общим heap backend. Это не отдельный CEVA pool.

Следствия для нового provider:

- каждое выделение должно иметь владельца, размер и состояние outstanding;
- `free` должен принимать только ранее выданный этому CEVA-сеансу указатель;
- остановка/timeout кодека должна освобождать outstanding allocations;
- нельзя отдавать адрес произвольного системного heap до определения доступной
  CEVA области и alias/cache правил.

## Cache и alias

Перед публикацией ARM→CEVA command pointer (`0x90532030`), ARM response pointer
(`0x90532034`) и перед стартом CEVA оригинал:

1. сохраняет CPSR и маскирует IRQ/FIQ;
2. повторяет ARM926 `test-and-clean D-cache` до завершения;
3. выполняет `drain write buffer`;
4. восстанавливает прежние IRQ/FIQ mask bits;
5. публикует указатель в MMIO.

Для входящих данных явного invalidate нет: ARM читает адрес CEVA после
`OR 0x10000000`. Это согласуется с гипотезой об uncached/coherent alias, но
реальная MMU mapping ещё не восстановлена. Поэтому alias нельзя объявлять
универсальным или применять к произвольному указателю.

Ответ CEVA→ARM готовится так: сначала записывается status/ack bit `0x02`, затем
сохраняется указатель, выполняется clean/drain и только потом pointer
публикуется через `0x90532034`. Семантика bit `0x02` как ACK/prepare
подтверждена порядком, но механизм уведомления CEVA отдельно ещё не доказан.

## Следующий шаг

1. Восстановить MMU/cache mapping для alias `0x10000000`.
2. Найти жизненный цикл общего heap и закрытия CEVA-сеанса.
3. Разобрать значения LCD format/mode и scaler fields по вызывающим кодекам.
4. Связать добавленный provider state machine с будущими bounded wait и
   cleanup callbacks, пока без MMIO backend.
5. Только затем готовить read-only JPEG probe с конечными timeout и cleanup.

Чистая C-модель этого state machine уже добавлена в `codec_lab`. Она не имеет
MMIO backend, проверяет payload/opcode, разрешает новые CEVA allocations только
в состояниях READY/OS_INT_LOADED/CODEC_BOOTED, запрещает повторный/неизвестный
free и не завершает STOPPING, пока остаются outstanding allocations. Host-тесты
и ARMv5 soft-float объект проверяют модель; это `ARM_OBJECT_ONLY`, не
`DEVICE_TESTED`. Предел 16 записей и общий лимит байтов — защитная политика
новой модели, а не восстановленное ограничение OEM allocator.
