# Этап 12: аппаратный журнал SD0 и ограничение native GetKeys

**Позднее уточнение:** BACK — короткий POWER; HOLD отдельный. Итого 16, а не
предварительные 15 органов управления. [Этап 13](STAGE13_REPORT_RU.md) содержит
новый RAM observer и исправленный сценарий POWER/HOLD. Ниже — история этапа 12.

14 ноября 2026. Пользователь прислал `SPMPKEYS.CSV` после исправления SD path.
Исходный файл сохранён без изменений в
[evidence/hardware/input_sd0_user_console_01.csv](evidence/hardware/input_sd0_user_console_01.csv).
4380 байт, SHA-256 `7aaf1a323317e073f95efa525081cfd760118f4d3df5aa68915f1053013f4732`.

Это пользовательское аппаратное свидетельство сохранённого журнала SD0_R2.
Метаданные указывают `/fat20a0/hda0/SPMPKEYS.CSV` и совпадают с ожидаемым профилем
пакета SPMP_INPUT_SD0.bin, artifact 14090758906. Хеш реально запущенного BIN
отдельно с консоли не прочитан; embedded source SHA — константа сборки, а не
измерение прошивки в RAM. Исправление SD0 получило положительное свидетельство
одного сеанса, а не гарантию любых файловых операций на любом устройстве.

## Что есть в журнале

Один сеанс, 76 событий: 14 PROMPT, 54 KEY, 7 SAMPLE, 1 END. Повреждённых,
игнорируемых или частичных строк нет. Все 27 нажатий имеют соответствующие
отпускания; pressed/released согласуются с переходами маски. Номер опроса и
штатное время не убывают. Последняя маска нулевая.

Все 13 подсказок и FREE пройдены. END записан при poll=2904 и time=60010 native
units, до предела 3000 опросов. Это продвижение штатного таймера, не независимое
измерение длительности секунд. END предшествует последнему close/FG restore/
возврату в исходнике: журнал не доказывает успешность каждого последующего шага.
Нет MENU-событий, поэтому действия LIVE/MAP/EXIT этим логом не подтверждены.
Несколько записей/open+seek циклов сохранились в одном файле, но только один
сеанс не проверяет сохранность старого файла при повторном запуске.

| Подсказка | Сохранённая cooked-маска | Нажатий / отпусканий |
|---|---|---|
| UP | `0x00000001` | 2 / 2 |
| DOWN | `0x00000002` | 4 / 4 |
| LEFT | `0x00000004` | 8 / 8 |
| RIGHT | `0x00000008` | 4 / 4 |
| A | `0x00010000` | 2 / 2 |
| B | `0x00020000` | 3 / 3 |
| START | `0x00002000` | 4 / 4 |

Это образцы по подсказкам оператора. Физические надписи не распознаются
автоматически; профиль одной консоли не распространяется на остальные.
[Кандидатный профиль](device_profiles/defender_multimix_magic_user_console_01.json)
сохранён как неполный и без автоматического применения.

## Неполная карта — не отсутствующие кнопки

Пользователь уточнил: X, Y, L, R, SELECT, BACK есть на консоли и нажимались
во время соответствующих подсказок. Для них не зарегистрировано ненулевых
cooked-кодов. Это не основание объявлять кнопки отсутствующими или неисправными.
Громкость + и − также присутствуют: **это отдельные кнопки, не алиасы L/R**.
В старом тесте для громкости не было подсказок, их коды не измерены.
Всего получаем 15 физических кнопок: 7 с образцами, 6 нажимавшихся без cooked
образцов и 2 кнопки громкости, не включённые в сценарий.

## Где теряются данные

Слот +0x100 ведёт к `native_get_key_input 0x2D2F7C`, затем к
`native_cooked_key_core 0x2D2FFC`. Для BIN/native kind6 этот код передаёт только
восемь возможных игровых масок, а не все биты нижнего collector:

| Маска collector до cooked filter | Результат |
|---|---|
| `1/2/4/8` | те же биты направлений |
| `0x10/0x20` | `0x10000/0x20000` |
| `0x800` | `0x2000` |
| `0x80000` | `0x80000` |
| `0x100/0x200` при volume gate0 | штатные действия громкости, без игрового бита |
| `0x1000` | системный pause/GUI путь, игровая маска обнулена |
| прочие одиночные биты, включая `0x40/0x80/0x400` | нулевой игровой результат |

[tools/audit_input_filter.py](tools/audit_input_filter.py) повторно исполняет
оригинальный ARM-код для всех **32** одиночных collector bits с kind6 и gate0;
выход +4, сохранность слова +0, изменения уровня громкости и pause callbacks
проверены. Backend эффектов полностью подменён; контроллер/GPIO не вызываются.
[Результат](evidence/input_filter_arm.json). Это расширяет прежнюю проверку
этапа 4. Результат не назначает raw-биты физическим X/Y/L/R/SELECT/BACK.

Лог V1 содержит только cooked output: нельзя установить, какая из ненаблюдаемых
кнопок была отсечена cooked core, потерялась раньше collector или обрабатывалась
другим путём. Ни запись первого слова структуры (оно не заполняется API), ни
придумывание дополнительных cooked bits эту информацию не восстановят.

## Следующая диагностика

Нужен отдельный тест всех 15 кнопок, который сохраняет одновременно cooked keys
и предшествующие RAM state/event words `0x556144/0x556148` до и после вызова
GetKeys. Эти адреса выведены из оригинального collector и setters/getter,
не из предположений о GPIO. Это остаётся промежуточным слоем MMI, а не прямой
трассировкой контактов. Если и там кнопок нет, следующий этап — producer:
call sites state setter `0x2D2E2C` в `0x34CEBC/0x34E238/...` и event setter
`0x2D2E50` в `0x29E8E0/0x2D3E84`.

Нельзя вызывать collector дважды ради сравнения: он изменяет TTL/сброс latch.
Будущий наблюдатель должен только читать RAM рядом с единственным штатным
опросом; отдельно проверить образец-код, границы и совместимость перед запуском.
В этом этапе новый BIN не выпускается: сохранены аппаратные данные, неполный
профиль и проверена логика фильтра исходного RAP. RedBoot/RAP/NAND не изменялись.

Разбор файла воспроизводится текущим decoder; hashes/evidence сохраняют связь
с неизменённым CSV. Проверки parser и целостности public snapshot проходят.
