# Этап 4: контракты файлов, графики, ввода и памяти native BIN

Продолжена реконструкция оригинального `8000_MMI.RAP`. Экспорт из трёх GZF
расширен с 99 до **170 выбранных функций**: MMI — 139, RedBoot v3 — 27,
RedBoot v1 — 4. Новые 71 функции относятся к MMI и его backend-вызовам;
исследование RedBoot на этом этапе не расширялось. Полных собираемых исходников
заводской прошивки пока нет. C в `decompiled/` — псевдокод Ghidra.

Получены **17 типизированных объявлений** исследованного подмножества API:
[`src/mmi_native_abi.h`](src/mmi_native_abi.h). Это описания аргументов и
структур без привязки указателей к адресам. Числовая карта всех 85 слотов
сохраняется отдельно; наличие функции в таблице не означает, что весь её ABI
восстановлен.

## Основания и пределы проверки

Единственный целевой RAP имеет SHA-256
`5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.
Все GZF импортированы заново во временные базы Ghidra 12.2. Mapped bytes
сверены с оригиналами, исходные три GZF сохранили хеши. Используются те же
два исправления границ функций и noreturn context restore, что на этапе 3.
Предупреждения декомпилятора доступны в `decompiled/export_summary.json`;
их отсутствие не удостоверяет корректность C. Язык исходных баз ARM v8
по-прежнему требует ручной сверки с целевым ARMv5TE.

Имена API сопоставлены с открытым
[`uli/libspmp8k`](https://github.com/uli/libspmp8k/tree/5498e63cbe828f04dd3a7a2b8fb46da84e83d7cb),
commit `5498e63cbe828f04dd3a7a2b8fb46da84e83d7cb`. Это сравнительный источник
имён и кандидатов сигнатур. Его реализация не импортирована, а расхождения
с нашей прошивкой не скрываются. Точные пути, blob-хеши и авторство:
[`evidence/native_abi_reference.json`](evidence/native_abi_reference.json).

Два независимых вида проверки:

- `audit_stage4.py`: **56 проверок ARM-слов и прямых вызовов**, соответствие
  17 объявлений реальным слотам и отсутствие двух allocator API в native-таблице.
- `emulate_native_abi.py`: **99 сценариев оригинального ARM** в Unicorn,
  где файловые, графические, RTOS и прочие backend-функции подменены явно.
  Оригинал выполняет проверки аргументов, ветвления, запись результатов и
  операции над синтетической RAM. Проверены восстановление SP и сохранение
  r4–r11 на этих путях. Заглушки backend сохраняют остальные регистры;
  это не доказательство всех обязательств ABI или поведения при вытеснении.

В VM нет MMIO, настоящих файлов устройства, кнопок, аудио или LCD. Размеры
320×240 в части fixtures и 2×3 в тестах копирования/очистки заданы тестом.
Результаты сохранены в `evidence/stage4_verified.json` и
`evidence/native_abi_arm_emulation.json`. Публичные тесты сравнивают host-модели
со снятыми результатами ARM без необходимости публиковать прошивку.

## Файловые операции: одинаковый статус, разные проверки

Все пять native-обёрток возвращают **32-битный статус 0 или 2**.
Аргументы передаются в r0–r3; `read/write` записывают фактический результат
backend в `int32_t *done`. Значение `-1` в этом поле возможно.

| Слот | Адрес | Восстановленный контракт |
|---|---|---|
| +0x13C | 0x462A74 | open(name, flags, out_fd): fd может быть 0; после open выполняется stat |
| +0x140 | 0x462B48 | read(fd, buffer, count, done): fd=0 отвергается до backend; остальные передаются дальше |
| +0x144 | 0x462BB0 | write(fd, buffer, count, done): допускается unsigned fd≤32, включая 0 |
| +0x148 | 0x462C14 | close(fd): unsigned fd≤32; backend<0 означает статус 2 |
| +0x14C | 0x462C64 | seek(fd, offset32, whence): статус по знаку backend, новая позиция отбрасывается |

Для `read/write` успех означает **ровно count байт**. Короткая передача или EOF
даёт статус 2, но поле `done` уже записано. Если wrapper отверг fd до вызова,
поле не меняется. В частности, read отвергает fd=0, хотя open может его выдать;
write/close отвергают -1 через беззнаковое сравнение, а read передаёт его backend.

Open конкатенирует строку по `*(0x6769F4)` с именем в локальный буфер 512 байт.
Контроль суммарной длины в этой обёртке отсутствует. Сам wrapper не сообщает,
какая строка находится по этому указателю во время конкретного запуска.
Если open успешен, а stat отрицателен, wrapper возвращает 2 без установки
out_fd и **без close**. Это потенциальная утечка дескриптора на этом пути.

Внешний libgame объявляет `fsSeek` как uint64_t. Здесь ARM проверяет r0
после `0x2EB69C` и заменяет его на 0/2. Нижний backend использует 32-битный
offset через адрес локального слова. Оснований возвращать вызывающему
64-битную позицию нет. Ghidra также выводит лишнюю 64-битность у read:
оставшееся значение r1 нельзя автоматически считать старшей половиной результата.

## Графика: размеры, владение изображениями и копирование

| Слот | Адрес | Проверенный смысл |
|---|---|---|
| +0x10 | 0x2DD20C | Paint: flip, копирование и обновление указателя контекста при разных буферах |
| +0x14 | 0x2DD80C | LoadImage(descriptor, out_id): регистрация переданного указателя |
| +0x18 | 0x2DDA44 | FreeImage(id): очистка записи, освобождение данных зависит от ownership-флага |
| +0x3C/+0x40 | 0x2DDE1C/34 | Set/Get ROP: значение/выходной указатель на один байт; проверено статически |
| +0x44/+0x48 | 0x2DDE4C/A0 | Set/Get FG: три байта RGB ↔ упакованное 16-битное значение |
| +0x58 | 0x2DE020 | выходной rect: x=y=0, width/height из callback-функций |
| +0x90 | 0x2DE06C | gate по младшим 16 битам размеров; затем очистка текущего буфера |
| +0x94 | 0x2DE124 | два выхода uint16_t: width и height |
| +0xA4 | 0x2DDB80 | QueryImage(id8, field8, uint16_t *out), **три аргумента** |

`GetFrameBuffer` не возвращает адрес пикселей. `SetFrameBuffer` принимает
значения 0..1023 после усечения до 16 бит, остальные отвергает с 0x70000401.
Принятые размеры не используются для resize или размера очистки: берутся
текущие width/height из callback-слотов 0x557014/0x557018.
Если указатели двух буферов различаются, очищается результат getter по
0x55700C, размером driver_width×driver_height×2. Затем вызывается cache-sync.
Например, запрос 0×0 в VM с backend 2×3 всё равно очищает 12 байт.

Paint при разных указателях вызывает flip через 0x55701C, после него заново
получает адреса и копирует width×height×2 из getter 0x557010 в getter 0x55700C.
Затем выполняет cache-sync и обновляет поле destination context. При одинаковых
указателях этот блок пропускается. В VM getter-функции возвращали постоянные
указатели; настоящее переключение дисплейного контроллера не эмулировалось.

Инициализация 0x2DF000 выбирает динамические callback-адреса из структуры
0x557658 либо резервные функции/буферы с фиксированными размерами 320×240.
Поэтому адрес getter-глобала нельзя подменять предполагаемым постоянным адресом LCD.

RGB-преобразование FG совпадает с RGB565:
`((r & 0xf8) << 8) | ((g & 0xfc) << 3) | (b >> 3)`.
Обратное преобразование оставляет младшие биты нулевыми: максимум 248/252/248,
а не 255/255/255. Это проверка представления FG, не полная идентификация LCD HAL.

LoadImage использует наблюдаемый 24-байтный **префикс** descriptor, полный
размер структуры не установлен. Пиксели и палитра заимствуются у вызывающего;
копии пикселей и перевода всех типов в общий формат здесь нет. Для type=1
ширина должна быть чётной, для type=2 — кратной четырём, иначе 0x406.
Путь shared palette может обнулить palette_entries в переданном descriptor,
поэтому его аргумент не объявлен const. Эта ветка в VM не проверялась.

Cache record имеет шаг 0x24. LoadImage выставляет ownership-флаг +0x1B=0.
Последующий FreeImage очищает запись, но не освобождает такие заимствованные
пиксели/палитру. До завершения использования изображения их память должна
оставаться действительной. Ветка ownership=1 и совместное освобождение палитр
экспортированы, но не покрыты новыми VM-сценариями.

QueryImage проверяет active и диапазон **2≤id<count**, где count — uint16_t
по 0x557028. Selector 1/2/3/4 возвращает width/height/младшие 16 бит type/shared-id
в uint16_t по r2. Остальные значения дают 0x406, выход не меняется.
Имя из внешней библиотеки не позволяет заменить эту сигнатуру её двухаргументным вариантом.

## Кнопки: wrapper содержит системные действия

Слот +0x100 → 0x2D2F7C принимает указатель, пишет только слово **+4** и возвращает
1 даже при отсутствии клавиш. Слово +0 остаётся прежним. Расположение остальных
полей возможной полной структуры не установлено.

Для native kind=6 (путь BIN) core 0x2D2FFC преобразует предсобранную маску:

| Входная маска | Выход |
|---|---|
| 0x1/0x2/0x4/0x8 | те же биты |
| 0x10/0x20 | 0x10000/0x20000 |
| 0x80000 | 0x80000 |
| 0x800 | 0x2000, если до этой проверки raw не очищен |
| 0x1000 | приоритетный системный путь; выходные keys=0 |

На 0x1000 вызываются команда 0xD07, GUI-действие, сообщение 0x569,
native pause-control и delay с аргументами (30,0). Интерпретация реального
времени задержки требует частоты RTOS tick; 30 не объявляются миллисекундами.

При нулевом gate по 0x55BD50, raw 0x200/0x100 увеличивает/уменьшает громкость
по 0x693C58 с границами 0..31 и вызывает два backend. После обработки raw
обнуляется: это подавляет обработку 0x800 в том же опросе. Если оба volume-бита
установлены, выигрывает увеличение. Уже выставленные обычные кнопки сохраняются.
Host-модель ограничена корректным исходным уровнем громкости 0..31.

Для kind=8 возвращается один приоритетный код, а не объединение битов:
маски 1,2,4,8,0x800,0x20,0x10 проверяются в этом порядке и дают
0x1C00,0x1E00,0x0200,0x0400,0x1A00,0x8000,0x4000.
Другие kind и их начальное состояние выхода не моделируются.

Если глобал 0x55BD04 равен 1, wrapper сначала получает cooked keys во временную
структуру. При нулевом результате берёт значение через 0x350630/0x350758.
В VM проверены оба исхода. Изменение этого глобала другим потоком между чтениями
и поведение реального input-device не проверены.

Нижний collector 0x2D2E6C читает event/state-переменные 0x556144/0x556148,
использует таблицы преобразования, сбрасывает состояние при активном меню и
на одном пути убирает 0x800. Это ещё не трассировка GPIO. Имена физических
кнопок из этой маски автоматически не следуют.

## Память: два allocator не взаимозаменяемы

В native-таблице из 85 слотов **нет** указателей на следующие функции:

| Функция | Адрес | Наблюдаемое поведение |
|---|---|---|
| general alloc/free | 0x299588 / 0x2995D0 | heap object через *(0x514250); alloc(0)=NULL, малые ненулевые размеры передаются backend |
| game pool alloc/free | 0x2E3724 / 0x2E3784 | pool object 0x606348; alloc(size<0x8000)=NULL; большие размеры передаются backend |
| game pool info | 0x2E37C0 | очищает 11 слов результата; переносит положительные значения backend-info |

Оба alloc проверяют выравнивание ненулевого результата на 4 байта через
assert-функцию. VM-сценарии используют выровненные результаты или NULL,
поведение assertion/error path не воспроизводится. Free/info экспортированы
и просмотрены статически; они не включены в новые динамические проверки.

Нельзя объявлять 0x2E3724 универсальным malloc: он отвергает небольшие размеры.
Нельзя также добавлять его адрес как отсутствующий слот API. Существование
пула само по себе не задаёт область RAM для SPMP-OS. Ещё предстоит восстановить
границы выделенного Game thread блока, служебные резервы и время жизни
callback/буферов при возврате приложения.

## Что готово для следующего этапа

Подготовлены типы, числовые layouts, C/ASM и host-модели выбранных проверок;
не подключены живые функции прошивки к HAL SPMP-OS. Не исследованы полностью
audio/resource API, threading/reentrancy, поведение всех графических операций,
backends FS/LCD, допустимые RAM-границы и полная сохранность RTOS-контекста.
Слот +0x138 здесь возвращает 0xFF; +0x150 — NULL, +0x154 за пределами таблицы.

Следующее: проследить резервирование/освобождение памяти Game thread, звук и
условия штатного возврата; сопоставить их с известным рабочим OEM BIN.
Для RedBoot остаются выбор варианта платы, реальный bootcfg/customize и
политика размещения секций. Аппаратного запуска, изменения прошивки или
создания пакета для Flash/NAND на этом этапе не было.

## Воспроизведение

```sh
# Без закрытых образов и Unicorn: 25 Python-тестов, 1 optional SKIP, 3 C-модели.
make -C research/boot_reconstruction test

# С локальным оригиналом: все 25 Python-тестов, без SKIP.
SPMP_MMI_RAP=/path/to/8000_MMI.RAP make -C research/boot_reconstruction test
python3 research/boot_reconstruction/tools/audit_stage4.py \
  --rap /path/to/8000_MMI.RAP --output work/stage4.json

# Требуются Unicorn 2.1.4 и локальный RAP; только RAM-only VM.
python3 research/boot_reconstruction/tools/emulate_native_abi.py \
  --rap /path/to/8000_MMI.RAP --output work/native-abi-arm.json
```

Для свежего экспорта используется `tools/run_ghidra_boot.py` с планом
`ghidra_targets.json`, Ghidra 12.2 и JDK 25; параметры описаны через `--help`.
Исходные образы/GZF остаются локальными. CI проверяет публичные тесты и
синтаксис объявлений для ARMv5TE soft-float; это не запуск приложения на ARM.
