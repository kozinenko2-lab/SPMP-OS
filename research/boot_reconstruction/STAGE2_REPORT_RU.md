# Этап 2: декомпиляция Ghidra, bootcfg и контракты старта MMI

## Результат и происхождение

В Ghidra 12.2 с JDK 25 открыты все три пользовательские GZF. Экспортирован
псевдокод **57 выбранных функций**: 21 RedBoot v3, 4 RedBoot v1, 32 MMI.
Это часть функций, не полная декомпиляция прошивки. Число распознанных функций
в исходных базах: RedBoot v3 — 601, v1 — 668, MMI — 7445.
Для двух потоковых функций MMI созданы границы в временной рабочей копии.
Сохранённые в экспорте имена добавлены исследованием, а не восстановлены
как оригинальные имена производителя.

Полный текст и выбранные листинги: `decompiled/`. Списки `functions.tsv`
содержат индекс известных функций каждой базы, а не их полный исходный код.
`ghidra_targets.json` фиксирует адреса, первые инструкции и хеши входов.

Перед экспортом проверены SHA-256 оригиналов/GZF и совпадение байтов каждого
загруженного низкого сегмента базы с оригинальным RAP/PRAW. Совпали 2 сегмента
MMI и по 4 сегмента RedBoot; высокие сегменты не отображены в этих GZF и явно
обозначены NOT_MAPPED. Пустая запись MMI отдельно обозначена EMPTY.
Все исходные GZF после обработки сохранили первоначальные SHA-256.

У баз исходно выбран язык `ARM:LE:32:v8`, хотя целевой процессор ARMv5TE.
В этом проходе язык не менялся: сохранялся пользовательский анализ.
ARM-инструкции критических участков дополнительно сверялись по оригиналу.
Псевдокод CP15/CPSR и прочих особенностей CPU требует ручной проверки ARMv5.

## 1. Выбор ветви загрузки в RedBoot v3/v5

По 0x45D78 функция сначала сбрасывает свои глобальные флаги. Дальнейшая
обработка отменяется, если getBootConfig не сработал, установлен бит ISP
(бит 31 регистра 0x9D80700C) или нет бита 0x10 в слове конфигурации по +0x04.
getBootConfig 0x33A84 копирует 0x138 байт из 0x1242C и возвращает 1.
Фактическое заполнение этой исходной структуры до данного места ещё не разобрано.

Подтверждённые биты **слова по +0x18**:

| Маска | Наблюдаемый эффект | Глобальная переменная |
|---|---|---|
| 0x00000001 | `[Enable ethernet]` | 0x171EC |
| 0x00000002 | `[Disable USB]` | 0x174D4 |
| 0x00000004 | `[Exec kernel]` | 0x171F4 |
| 0x00000008 | запрос customize; отдельный helper, до apply_bootcfg | читается напрямую |
| 0x40000000 | `[Load romfs]` | 0x171E8 |
| 0x00000080 | `[linux boot]`, учитывается только внутри Load romfs | 0x174DC |
| 0x20000000 | `[Fast boot]`, только если Exec kernel уже установлен | 0x171F0 |

В main 0x46904 существующий указатель boot-скрипта имеет приоритет над
автоматической загрузкой. Если его нет и Exec kernel установлен:

- Load romfs выключен → путь 0x3E8E8 через NAND-образ.
- Load romfs включён и Fast boot включён → 0x36AB4, всегда `8000_mmi.rap`.
- Обычный ROMFS + Linux → буферная загрузка `linux_kernel.rap`.
- Обычный ROMFS без Linux → буферная загрузка `8000_mmi.rap`.

Строка `go -c` выбирается по Linux-флагу, а не непосредственно по типу
загруженного файла. При сочетании Fast+Linux выбирается MMI, но генерируется
`go` без `-c`. Это наблюдаемая логика, не рекомендация менять конфигурацию.
Точное значение bootcfg на пользовательской консоли неизвестно.

Модель этих условий: `src/redboot_boot_policy.c`. Применимость доказана для
разобранного семейства v3/v5; автоматическое перенесение адресов на v1/v2/v4
недопустимо.

В двух местах результат загрузчика проверяется только на ноль. Возвращаемые
парсером отрицательные коды также проходят эту проверку. Например, -1 затем
может быть отвергнут обработчиком go как sentinel. Другие ошибочные значения
требуют отдельного анализа конечного поведения. Нельзя считать ненулевой
результат достоверным адресом запуска. Модель сохраняет эту особенность OEM,
но не используется как валидатор нового загрузчика.

## 2. Механизм customize.o и реальный ELF-контракт

Подтверждены mount `/dev/nf2` → `/Rom` с типом `romfs` (0x369FC), затем при
запросе customize — загрузка `/Rom/image/customize.o` и поиск `func_customize`.
Бит запроса берётся helper 0x33EF4 напрямую из исходного слова +0x18;
его чтение предшествует разбору остальных bootcfg-флагов.

0x40A14 проверяет ELF magic, ELFCLASS32=1, EI_DATA=1, e_type=1 (ET_REL),
e_machine=40 (ARM), читает section headers, `.symtab`, `.strtab`, размещает
данные и обрабатывает релокации. Это другой формат, чем MMPi RAP.
После размещения вызывается функция обслуживания cache/TLB 0x41350,
затем, если найден, `library_open()`. Только после возврата из module-open
внешний загрузчик ищет `func_customize` и сохраняет его по 0x252C.

Исходная таблица внешних символов по 0x17990, count=5 по 0x1798C:

| Имя | Адрес v3/v5 |
|---|---|
| diag_printf | 0x4563C |
| GetCxRefClockFreq | 0x33BF0 |
| __udivsi3 | 0x4BC08 |
| cyg_thread_delay | 0x34850 |
| setLcmSWRotationType | 0x3484C |

Это исходное содержимое таблицы, а не доказательство отсутствия её изменений
во время выполнения. Совпадение имён не подтверждает все сигнатуры API.
В библиотечном загрузчике есть разрешение собственных и внешних символов.

Обработчик 0x413D0 принимает только типы **1, 2, 28, 29**:
R_ARM_PC24, R_ARM_ABS32, R_ARM_CALL, R_ARM_JUMP24. Остальные идут в сообщение
Unknown relocation и возвращают -1. Для branch-релокаций сохраняется верхний
байт инструкции, пересчитывается 24-битный immediate; проверки дальности и
выравнивания в этом обработчике нет. Для ABS32 прибавляется адрес символа.
`src/redboot_reloc_model.c` воспроизводит арифметику без записи в память консоли.

Диспетчер выбирает section types 4 и 9, но исследованный цикл разбирает записи
с шагом 8 байт. Поддержка полноценного ELF32 RELA с 12-байтными записями
не подтверждена; нельзя объявлять загрузчик универсальным.

Обёртка 0x36844 вызывает callback, если указатель не нулевой. Наблюдаемые r0:

| Значение | Callsite | Место в последовательности |
|---|---|---|
| 0 | 0x46974 | после попытки загрузки customize.o |
| 1 | 0x469CC | перед инициализацией ряда RAM globals |
| 2 | 0x46AD0 | после bootcfg, init-таблицы и вывода баннера |
| 3 | 0x46D24 | в цикле обработки ввода после результата, отличного от timeout |

Это числовые этапы, не восстановленные имена enum производителя.
Возврат callback не используется обёрткой как управление запуском.
Загрузчик customize возвращает 1 даже если `func_customize` не найден:
существенен сам указатель. Отсутствующий файл возвращает 0.

В облегчённом архиве нет извлечённого `customize.o`, а ROMFS-ресурсы неполны.
Наличие, содержимое модуля и возможность использовать этот путь на Defender
не установлены. Пакет для устройства не создавался.

## 3. MMI: поток системной инициализации и события

0x4475C0 создаёт поток с entry=0x447540, priority=12, stack_size=0x2980,
если его handle равен нулю, и затем вызывает resume-обёртку 0x339B6C.
В GZF точка входа не была определена как функция; она восстановлена по
проверенному ARM-прологу в рабочей копии. Аналогично восстановлена 0x4473BC.

Системный поток:

```text
flag_init(0x68E4D0)
flag_init(0x68E4C8)
0x2886F0()                         // возврат в этом месте не проверяется
flag_wait(0x68E4C8, mask=1, mode=3) // возврат также не проверяется
если *(0x55613C) != 1: 0x2D1B28()
flag_setbits(0x5EF634, 1)
0x4474D8()                         // до 10 попыток и уведомление
0x2D8B88(0x581, 0, 0)
0x447458()                         // создать/возобновить background
0x339B04()                         // обёртка выхода текущего потока
```

Производитель события 0x2D2C28 выставляет бит 1 в 0x68E4C8:
в нормальной ветке и перед каждым из двух return -1. Поэтому событие означает
завершение соответствующей операции, но не удостоверяет её успех.
Назначение всех вызываемых им подсистем ещё не восстановлено.

В 0x4474D8 до десяти раз вызывается 0x438394(2), с задержкой 10 между
неудачными попытками; после успеха **или исчерпания попыток** выставляется
бит 1 события 0x68E4D0. Считать его безусловным признаком успеха тоже нельзя.
Единицы задержки не установлены как миллисекунды.

Из ядра flag-poll 0x33CE74 установлены именно числовые значения этой сборки:
bit 1 (маска 2) — OR, bit 0 (маска 1) — clear. Mode=3 — OR+clear.
При совпадении возвращается всё текущее слово flags, и clear обнуляет всё
слово, а не только запрошенную маску. Модель: `src/mmi_flag_model.c`.
Это немедленная проверка; блокирующее ожидание и планировщик в модель не входят.
Подключаться к этим объектам событий из SPMP-OS без восстановления контракта
нельзя: сторонний wait может поглотить уведомление штатного потока.

## 4. Что это даёт для модернизации

Появились проверяемые кандидаты: штатный ELF-модуль customize и оболочка поверх
уже инициализированной MMI/eCos. Ни один ещё не является готовым способом
загрузки. Перед реализацией нужны:

1. Исследовать реальный customize.o и происхождение bootcfg конкретной платы.
2. Установить ABI callback/экспортов и ограничения выделяемой модулю памяти.
3. Разобрать 0x2886F0, 0x2D2C28, 0x438394 и реальные критерии готовности.
4. Дойти до GUI event loop, native-app loader и проверенных display/input API.
5. Уточнить ARMv5-интерпретацию системных регистров и высоких сегментов,
   отсутствующих в пользовательских GZF.

## 5. Проверки и воспроизведение

- Три GZF: хеши и память сверены, 57/57 выбранных функций экспортированы.
- Дополнительный `audit_stage2.py`: 38 инструкций ARM, 29 элементов dispatch
  релокаций, 5 экспортов, callsites и литералы объектов событий.
- Три host C-модели: boot policy, relocation arithmetic, flag poll — тесты пройдены.
- Исходные образы и GZF не менялись. Аппаратных испытаний не было.

```sh
make -C research/boot_reconstruction test
python3 research/boot_reconstruction/tools/audit_stage2.py /path/to/private/archive-root --output research/boot_reconstruction/build/stage2.json
python3 research/boot_reconstruction/tools/run_ghidra_boot.py \
  --inputs /path/to/private/archive-root --ghidra /path/to/ghidra_12.2_PUBLIC \
  --jdk /path/to/jdk25 --scratch /path/to/local-scratch --output /path/to/new-export
```

Первый вызов не требует прошивки, два последних используют локальные оригиналы
и GZF. Raw-экстракты и временные базы удаляются runner после завершения;
экспорт текста остаётся локально. Скрипт проверяет все итоговые статусы, поскольку
analyzeHeadless может вернуть код 0 даже при ошибке отдельного GhidraScript.
