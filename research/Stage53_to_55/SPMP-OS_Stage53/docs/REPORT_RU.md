# SPMP-OS — Stage 53: архитектура RedBoot и MMI по пользовательским Ghidra GZF

**Дата:** 13 ноября 2026. **Материалы:** `/mnt/data/SPMP8k.zip` — три пользовательские базы Ghidra `.gzf`, исходные бинарники Defender, подготовленные для Ghidra ELF из Stage 52. **Запись Flash/NAND:** не выполнялась. **Патчей RedBoot/MMI для установки:** нет.

## 0. Состояние и ограничения

Реально проверены заголовки, CRC и дефлирование **всех трёх** `.gzf`; извлечены внутренние Ghidra базы (MMI: 45 629 440 байт, RedBoot v1: 4 423 680, v3: 3 997 696). В таблицах базы встречаются **7 437 / 665 / 598 различных имён `FUN_...`** соответственно. Это признаки сохранённого анализа, но **не доказательство того, что декомпилировано столько работоспособных функций**, и не число полностью восстановленных системных API. Ранее подготовленные имена вроде `MMI_reset_00280040` попали в Ghidra при импорте Stage 52; это НЕ независимое подтверждение их назначения.

Среда анализа не содержит установленного Ghidra Decompiler, поэтому текст C-псевдокода из баз сейчас не получен. Для воспроизводимого извлечения всех функций, связей и конкретных декомпиляций приложен **Java GhidraScript** `ghidra_scripts/SPMP_ExportArchitecture.java`. Он **ничего не изменяет** в открытой базе.

Выводы ниже проверены параллельным чтением оригинальных машинных слов ARM из точных сегментов RAP/PRAW, а не только по именам, выданным Ghidra.

## 1. Фактическая последовательность загрузки

```
SoC reset → OEM RedBoot (0x00030040)
    └─ ROMFS: /Rom/image/8000_mmi.rap
         ├─ RedBoot семейство 1: загрузка 0x0004A998 → loader 0x00038F0C
         └─ RedBoot семейство 3: загрузка 0x000467F4 → loader 0x00036BF4
              └─ аргумент загрузчика: 0x00A00000 (его роль уточняется)
                   └─ MMP/RAP-сегменты MMI по привязанным адресам
                        └─ MMI entry 0x00280040
                             ├─ CP15, режимы CPU, векторы исключений, стеки
                             ├─ очистка RAM (см. ниже)
                             ├─ инициализация ядра/служб/драйверов eCos
                             ├─ файловая система, SD, LCD, PCM, кнопки
                             └─ оболочка + менеджер запуска игр/native BIN
```

**Граница важна:** аргумент 0x00A00000 в RedBoot и стартовый адрес 0x00280040 в собственном RAP — **разные факты**. Не следует ни считать `0x00A00000` свободной памятью, ни считать его окончательным местом выполнения всей MMI. Не восстановен весь handoff между стадиями и не доказаны правила передачи ABI.

### Доказанные инструкции

| Элемент | Адреса | Что проверено в машинном коде |
|---|---|---|
| RedBoot v1 фабричная загрузка | 0x0004A9BC, 0x0004A9C0, 0x0004A9C4 | R0 = ptr `/Rom/image/8000_mmi.rap`; R1 = 0x00A00000; BL 0x00038F0C |
| RedBoot v3 фабричная загрузка | 0x00046810, 0x00046814, 0x00046818 | Те же аргументы; BL 0x00036BF4 |
| MMI reset | 0x00280040 | MRC CP15, изменение управляющего регистра |
| MMI копирование векторов | 0x00280060–0x002800EC | Запись в низкие адреса векторов ARM по условиям режима CPU |
| MMI очистка RAM | 0x00280120–0x00280138 | Цикл STR и сравнение границ |
| MMI продолжение старта | 0x0028013C–0x00280150 | Несколько BL перед переходом к основному запуску |
| MMI ожидание после выхода | 0x00280154 | `EAFFFFFE` — бесконечная петля |

### Память: запрет на произвольный RAM handoff

Литералы, используемые кодом очистки RAM, указывают диапазон **`0x0056AD90`–`0x006C8FDC`**. Область между границами обнуляется (включительность последнего слова следует из ветвления BLS; её следует ещё проверить декомпилятором). Значит, переносить лог RedBoot или размещать SPMP-OS поверх этого диапазона без исследования владения памятью нельзя. Это не полная карта свободной RAM, а лишь один опасный диапазон.

## 2. Из чего состоит `8000_MMI.RAP`

Это не «один исполняемый файл интерфейса». В нём есть ARM startup и обработчики исключений, RTOS-службы, файловая система, драйверы периферии, файловые и графические ABI, а также загрузчики приложений. По коду и проверенным адресам:

| Подсистема | Адрес / данные | Состояние |
|---|---|---|
| ARM startup, прерывания, память | 0x00280040 и следующие инструкции | Подтверждено машинным кодом |
| eCos FAT fileops | таблица 0x00513CDC: 10 указателей | Подтверждена содержимым ROM |
| FAT read / write / lseek | 0x00283F3C / 0x00283FC4 / 0x00284054 | Подтверждены записи таблицы; смысл ABI из eCos |
| FAT fsync / close | 0x00284100 / 0x00284108 | Адреса из таблицы; fsync ранее найден как возврат без записи |
| Диагностический stub | 0x00298B64 | `BX LR` — пустая функция |
| Соседний диагностический обработчик | 0x00298B68 | Имеет исполняемое тело и флаг состояния; назначение требуют трассировки |
| SD status poll | 0x002B9A38 | Поведение частично исследовано Stage 45 |
| SD отправитель команды | 0x002B9B78 | Прямые вызовы исследованы Stage 48 |
| Загрузка встроенного `n1.bin` | около 0x0046018C | Путь `/image/Game/n1.bin`, копирование и переход в RAM |
| Контейнер NGame | 0x004611BC | Проверка `NGame` через вызов сравнения 0x00345F54 |
| Конечный идентификатор BIN | около 0x004618C4 | Проверка `SUNPLUS556GAME` через сравнение 0x00345F54 |

Секция MMI кода и строк лежит начиная с 0x00280000; другой RAP-сегмент — у 0x006C8FE0. Это адреса памяти **после загрузки MMP**, не файловые оффсеты.

## 3. Почему не запускался наш NGame BIN

У штатной MMI есть **несколько маршрутов запуска**. Код `0x0046018C` загружает встроенный `/image/Game/n1.bin`; при 0x00460250/0x00460254 выполняется `MOV LR, PC; MOV PC, R3`, где R3 установлен в 0x00A00000. Это пример передачи управления ARM-коду, а **не доказательство, что произвольная BIN-игра с NGame-заголовком запускается таким же способом**.

Другой код (`0x004611BC`) сравнивает первые 5 байт с `NGame`, читает атрибуты по смещениям `+0x6D` и `+0x78`, далее проверяет завершающую строку `SUNPLUS556GAME` около `0x004618C4`. В MMI присутствуют строки `[NativeGE_loadGameBin]game identifier error`, `[gcGameParse] LCM resolution index: %d`. Это фактические следы особого контейнера, но остальные проверки (размер, контрольная сумма, шифрование, путь, версия, тип ресурса, вызов из UI) ещё не полностью доказаны.

**Следствие:** сообщение консоли «неверный формат» нельзя сводить к FAT или к отсутствию SDK. Нельзя продолжать генерировать NGame BIN вслепую: сначала нужна декомпиляция основной ветки валидатора, затем тест **в RAM** на штатном запускателе.

## 4. Две инженерные ветки для SPMP-OS

### Ветка A — модернизация существующей MMI (первая, с минимальным риском)

SPMP-OS стартует **внутри уже работающей MMI/eCos** как оболочка либо штатный модуль, не захватывая MMU, векторы исключений, SD и аппаратные прерывания. Сохраняются оригинальные RedBoot и заводская MMI. Используются подтверждённые native API и файловый слой после их ревизии. Уже созданные в проекте темы, файловый менеджер, мультимедиа и эмуляторы можно портировать на этот слой. Для восстановления после ошибки достаточно штатного выхода из модуля, **если ABI и механизм запуска действительно работают**. При ошибке нативного модуля зависание также возможно, но NAND не переписывается.

**Первая задача:** доказать из Ghidra валидатор NGame, ABI входа native-приложения, модель загрузки/выгрузки, где хранится таблица функций и как возвращается управление. Это решит проблему прошедших неудачных тестов и даст путь к первым реальным логам MMI после монтирования SD.

### Ветка B — автономная SPMP-OS (после A)

Отдельный ARMv5 startup, собственная RAM-разметка, таймер, IRQ, SD/FAT, LCD, PCM, GPIO-кнопки и supervisor. В первую очередь допустим **тестовый запуск из RAM** по подтверждённому OEM loader ABI, без изменения RedBoot и без записи во внутреннюю Flash. Нужны аппаратные карты регистров, проверка модели IRQ, временное отключение старой MMI, восстановление/перезапуск OEM без power cycle.

**Запуск через изменённый RedBoot с SD fallback** — отдельный поздний этап; даже наличие прошивочного recovery не делает ошибку в RedBoot безопасной. Без аппаратного bootrom/recovery/заводского бэкапа и платы восстановления исполняемый патч RedBoot не выпускать.

## 5. План восстановления ОС по приоритету

1. Экспортировать из существующих трёх GZF callgraph `calls.csv`, карту функций и декомпиляции ключевых узлов (прилагаемый Java GhidraScript). Это устранит слепые места вокруг handoff и проверки BIN.
2. Отследить из `MMI_reset` дерево вызовов: RTOS startup, процессы создания потоков, монтирование ROMFS/FAT, UI thread и диспетчер игр. Добавить имена и прототипы в отдельный каталог схем, не менять OEM бинарники.
3. Декомпилировать функции `0x004611BC`, `0x00461268`, `0x004618C4`, функцию вызывающего меню и все возвратные коды `NativeGE_loadGameBin`; сделать точный валидатор BIN на ПК для проверки до реального запуска.
4. Построить API-таблицу eCos/NativeGE: смещения в таблице, подписи функций, соглашение вызова (EABI / APCS), память стека и порядок инициализации. Сопоставить с `libspmp8k` как **референсом**, не как доказательством совместимости с Defender.
5. Разобрать взаимодействие MMI с framebuffer, аудио, кнопками и SD, сделать HAL совместимости. Первую версию оболочки SPMP-OS тестировать отдельным native-модулем без замены ROMFS.
6. Выяснить возможность загрузки независимого тестового образа в RAM и безопасного возврата к заводской MMI. Не менять запись NAND.
7. Лишь после подтверждения обеих веток — рассматривать fallback в RedBoot.

## 6. Как применить `SPMP_ExportArchitecture.java`

Файлы GZF **уже импортированы и проанализированы пользователем**. В Ghidra: File → Configure → Script Manager → `Manage Script Directories` → добавь каталог `ghidra_scripts` из этого архива. Открой один из проектов и выполни `SPMP_ExportArchitecture.java` через Script Manager (это **Java**, PyGhidra не требуется). Скрипт работает только на чтение, выгружает в `~/SPMP_OS_Ghidra_Export/<имя проекта>/`:

- `program.txt`, `memory.csv` — язык, сегменты, entrypoints;
- `functions.csv` — список функций, сигнатур, размера и конвенций;
- `calls.csv` — связи между найденными Ghidra функциями;
- `strings.csv` — типизированные строковые данные;
- `priority_references.csv` — ссылки на конкретные точки интереса;
- `decomp_*.c` — псевдокод ограниченного списка функций начальной загрузки, файловой системы и запускателей.

Скрипт не записывает изменения в проект Ghidra, не изменяет исходный RAP, не создаёт прошивки. **В этой среде Ghidra отсутствует, поэтому исполнение самого Java-скрипта не проверено**. Его результат будет зависеть от завершённости Auto Analyze и версии Ghidra. Выгрузка полной декомпиляции всех 7+ тыс. функций намеренно не предусмотрена (дорого и не обязательно для архитектуры).

Если нужен headless, после импорта GZF в локальный проект используется `support/analyzeHeadless PROJECT_DIR PROJECT_NAME -process PROGRAM_NAME -noanalysis -scriptPath PATH_TO_SCRIPTS -postScript SPMP_ExportArchitecture.java OUTPUT_DIR`. Имена PROGRAM_NAME бери непосредственно из своего проекта.

## 7. Отчёт о проверках

- Три пользовательских GZF: подтверждены Java/GZF magic, ZIP DEFLATE stream и CRC, распакована внутренняя Ghidra DB.
- Проверено 8700 различных символических имён `FUN_...` (7437 + 665 + 598), выгружены адресные индексы CSV.
- Сопоставлены с оригинальными бинарными сегментами: адрес фабричной MMI в обоих RedBoot, 0x00A00000, CP15, MMI reset, границы очистки RAM, механизм jump-to-game, пустой stub.
- Запущены пять Python unittest; все прошли.
- Ни один байт оригинального RedBoot, 8000_MMI.RAP и переданных GZF не модифицирован.

**Ключевое ограничение:** это рабочий архитектурный анализ и инструменты для извлечения псевдокода, но **не готовая собственная SPMP-OS**. На реальной консоли Stage 53 не запускался. Для изменения MMI/RAP нужна подтверждённая схема recovery и безопасная цепочка исполнения.
