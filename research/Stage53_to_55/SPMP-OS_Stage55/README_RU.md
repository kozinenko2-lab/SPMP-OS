# SPMP-OS Stage 55 — архитектура GUI, eCos и фоновых служб

Это **статическое исследование** оригинальной `8000_MMI.RAP`, а не готовая прошивка или патч RedBoot.

## Быстрый результат

- `0x003BE5B0` — **Demo GUI**: вызывает `0x00447640` ещё до других действий GUI (`BL` по адресу `0x003BE5CC`).
- `0x00447640` — системный координатор: выполняет прямой read-modify-write аппаратного адреса `0x90005040` (`LDR`, `ORR #7`, `STR`), вызывает множество вспомогательных функций и `0x004475C0`.
- `0x004475C0` — условное создание **Systen initial Thread** (`0x00447540`) с приоритетом 12, размером стека 10624 байта. Конкретные условия и порядок исполнения после планировщика не установлены.
- `0x00447540` — системный поток: инициализирует контекст служб; `BL 0x00447458` вызывает конструктор фонового потока, затем обращается к RTOS-функции `0x00339B04`.
- `0x00447458` — условное создание **Systen BackGround Thread** (`0x004473BC`) с приоритетом 30 и стеком 10624 байта.
- `0x004473BC` — фоновый поток, содержащий бесконечный цикл с явным переходом `0x00447450 → 0x004473F0`. Внутри цикл вызывает `0x00339BE8` с `r0=100` (единицы измерения ещё не установлены), а также сервисные функции.
- `0x00339AAC` — общий wrapper создания потока, вызывает `0x0033A2DC` и сохраняет handle в переданный адрес. Внутренний код содержит сообщение `Stack size too small`, что подчёркивает важность ABI стека.

**ВНИМАНИЕ:** семантика регистра `0x90005040` пока неизвестна. Это подтверждённый адрес записи, **не** разрешение модифицировать регистр. Данный анализ не демонстрирует, что запуск GUI можно пропустить.

## Материалы

- `evidence/stage55_verified_architecture.json` — все подтверждения и прямые вызовы в ограниченных функциях.
- `evidence/stage55_direct_calls.csv` — прямые вызовы `BL` и адреса вызываемых процедур.
- `evidence/stage55_literals.csv` — PC-relative литералы, найденные строки и параметры.
- `evidence/stage55_spawns.csv` — три системных потока и параметры их создания.
- `evidence/stage55_full_image_xrefs.csv` — прямые вызовы на выбранные адреса по всему исходному RAP.
- `evidence/stage55_startup_to_gui.dot` — граф запуска (пунктир = передача адреса потока, а не синхронный вызов).
- `ghidra_scripts/SPMP_Stage55_GUI_DeepExport.java` — **только чтение** в Ghidra; экспорт псевдокода, инструкций и входящих ссылок. Не редактирует Ghidra-проект, MMI или RedBoot.
- `tools/analyze_gui_boot.py` — повторяемый анализ с SHA-256 OEM; для запуска включает `tools/spmp_oem_arm.py`, адаптированный из Stage 54.

## Перепроверка

```bash
sh tools/run_stage55.sh /path/to/8000_MMI.RAP
# или вручную:
python3 tools/analyze_gui_boot.py --rap /path/to/8000_MMI.RAP --outdir evidence
SPMP_MMI_RAP=/path/to/8000_MMI.RAP python3 -m unittest discover -s tests -v
```

Тесты проверяют точные ARM-инструкции, адрес MMIO, создание потоков, обратную ветку фонового цикла, хеш, воспроизводимость таблиц и отказ на повреждённом OEM RAP.

### Декомпиляция при наличии локальной Ghidra

1. Открой базу GZF для MMI (не RedBoot) в CodeBrowser.
2. Добавь каталог `ghidra_scripts` в **Script Manager → Script Directories**.
3. Запусти `SPMP_Stage55_GUI_DeepExport.java` — результаты будут в `~/SPMP_OS_Stage55_Export`.
4. Если файл `target_functions.csv` содержит `NOT_DEFINED`, в CodeBrowser проверь адрес (`G`), выдели функцию (`F`) и повтори экспорт. Делай это только в **копии** Ghidra-проекта; операция меняет лишь локальную базу Ghidra.
5. Полученные `decomp_*.c`, `target_functions.csv`, `references.csv`, `instructions.txt` можно загрузить обратно для проверки вызовов виртуальных таблиц и состояния GUI.

Скрипт не запускался в самой Ghidra в этой рабочей среде; его API/результаты декомпиляции требуют проверки локально.

## Что делать с этим для SPMP-OS

**Самый безопасный путь:** оставить OEM RedBoot, eCos и аппаратный startup, выявить интерфейс сервисов и архитектуру сообщений, затем запускать собственную оболочку через совместимый механизм расширений MMI. Не подменять `Demo_GUI` до выяснения её обязательных вызовов и побочных эффектов.

Полностью независимую SPMP-OS можно развивать отдельно и испытывать через контролируемую загрузку в RAM, но этот пакет **не** доказывает её безопасность или совместимость с Defender.

Ни один OEM бинарник, ROMFS, Flash, NAND или RedBoot этим этапом не менялся.
