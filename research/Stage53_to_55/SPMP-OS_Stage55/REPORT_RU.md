# Stage 55 — точная карта запуска MMI/eCos и границы модернизации

**Исходник:** заводской `8000_MMI.RAP`, SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`. Оригинал предоставлен пользователем. Материалы Ghidra `SPMP8k.zip` ранее использованы для сверки адресов; текущие новые факты получены чтением исполняемых ARM-инструкций и проверены на точном оригинальном образе.

## 1. Реконструированная цепочка

| Адрес/место | Факт из ARM | Последствие |
|---|---|---|
| `0x00280040` | CP15 ARM startup, настройка памяти и переходы к системному bootstrap | Не заменять на произвольную точку входа |
| `0x00297CFC` → `0x002807C8` | Прямой `BL` к конструктору потока GUI | Создание GUI происходит после части startup |
| `0x00280810` → `0x00339AAC` | Запрос создания `Demo GUI`, `r1 = 0x003BE5B0`, приоритет 25, стек 0x4000 | GUI отдельный поток eCos |
| `0x003BE5CC` → `0x00447640` | `Demo GUI` вызывает системный координатор | Код GUI содержит системные обязанности |
| `0x00447668–0x0044767C` | `MOV r2,#0x90000000`; `ADD #0x5000`; `ADD #0x40`; `LDR r3,[r2]`; `ORR r3,#7`; `STR r3,[r2]` | Подтверждён MMIO read-modify-write адреса `0x90005040`; **неизвестно, что за регистр** |
| `0x004476B0` → `0x004475C0` | Создание системного потока через дополнительную обёртку | Системная инициализация инициируется из координатора |
| `0x00447610` → `0x00339AAC` | `Systen initial Thread`: entry `0x00447540`, приоритет 12, стек 10624 байта | Условное создание, не синхронный `BL` в тело потока |
| `0x004475A4` → `0x00447458` | Системный поток запускает конструктор фонового | Зависимость старта подсистем |
| `0x0044749C` → `0x00339AAC` | `Systen BackGround Thread`: entry `0x004473BC`, приоритет 30, стек 10624 байта | Фоновая служба самостоятельный поток |
| `0x00447450` → `0x004473F0` | Безусловный обратный переход | Фоновый рабочий цикл, в том числе вызовы сервисов |
| `0x00447448/4C` | `r0 = 100`, `BL 0x00339BE8` | Пауза/планировщик, единицы не установлены |
| `0x00339AF0` → `0x0033A2DC` | Внутренний механизм создания потоков | Нужно восстановить ABI состояния / scheduler |

Доказана статическая последовательность *вызовов и передачи адресов*. Это не запись динамического порядка выполнения потоков: планировщик может выбрать иной порядок после создания.

## 2. Прямые аппаратные побочные эффекты

Стандартный пользовательский интерфейс нельзя заменить одним прыжком на собственный код, иначе можно пропустить операции системной инициализации. Самый важный доказанный пример — `0x90005040`, изменяемый прямо из координатора GUI. Регистр **не идентифицирован** как GPIO, clock или LCD: эти назначения нельзя угадывать по адресу. Рекомендация: сохранить оригинальный координатор при первых тестах новой оболочки.

Поток начальной инициализации также обращается к RTOS-функциям и инициализирует ресурсы; его изъятие может повлиять на SD/FAT, питание или звук. Точные зависимости нуждаются в декомпиляции вспомогательных вызовов (`0x002886F0`, `0x00339F10`, `0x00339F64`, `0x002D8B88` и т. д.).

## 3. Функции, приоритетные для следующей декомпиляции

1. `0x003BE5B0` и `0x00447640` — грань GUI и системных обязанностей.
2. `0x00447540`, `0x004475C0`, `0x004474D8`, `0x00447458` — сервисный startup, условные ветви и создание фоновых потоков.
3. `0x004473BC` — постоянный цикл обслуживания и глобальное состояние `0x005623F4`.
4. `0x00339AAC`, `0x0033A2DC`, `0x00339B04`, `0x00339BE8` — ABI потоков, scheduler и задержки.
5. `0x003BE6A0` и `0x003BE6C0` — последующие действия GUI.

Для декомпиляции подготовлен Java GhidraScript (чтение, без правок программы), который экспортирует C-псевдокод там, где функция опознана Ghidra, а также машинные инструкции и источники ссылок.

## 4. Практические этапы SPMP-OS

**А. SPMP-OS Shell поверх eCos.** Точка входа — **после** штатной последовательности инициализации. Предварительно определяем механизмы событий GUI, ввод и дисплей; запускаем собственный экран с возможностью возврата. Без записи MMI/RedBoot в NAND. Риск сравнительно невысок, но native ABI и передача управления остаются неподтверждёнными на конкретной ревизии Defender.

**Б. Расширение заводской MMI.** После подтверждения API подключаем файловый менеджер, настройки и эмуляторы как изолированные модули. Заменять код в ROMFS только при наличии надёжного восстановления и проверки на железе; обычная замена RAP в NAND также способна лишить консоль штатной загрузки.

**В. Независимая SPMP-OS из RAM.** Собственная инициализация RAM/IRQ/cache и HAL, отдельный загрузочный контейнер и таймаут; RedBoot не модифицировать. Испытывать только после подтверждения адресов RAM, формата загрузки и возможности аппаратного восстановления. Возврат к заводской MMI после произвольного сбоя не гарантирован без исправного watchdog/аппаратного reset.

## 5. Что этот этап **не** доказывает

- Значение MMIO `0x90005040` и безопасность его модификации вне оригинального кода.
- Порядок фактического выполнения потоков и доступность их объектов в любой момент запуска.
- Возможность безопасно заменить `Demo GUI` без пропуска обязательных вызовов.
- Готовый бинарник SPMP-OS, запускаемый Defender.
- Прямое файловое логирование ранней загрузки MMI или RedBoot на SD.

**RedBoot и заводская прошивка не изменялись.** Все файлы Stage 55 — средства анализа и разработки, не флеш-образы.
