# SPMP-OS Stage 54 — как устроен запуск штатной MMI/eCos

## Цель и достоверность

Это **исследование оригинальной MMI, а не прошивка**. Полностью оставлены без изменений RedBoot, recovery, NAND и `8000_MMI.RAP`. Анализ выполнен на том же заводском `8000_MMI.RAP` (SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`) и учитывает предоставленные пользователем базы Ghidra из `SPMP8k.zip`/Stage 53. Выводы ниже проверены повторным чтением машинных ARM-инструкций OEM; **не являются наблюдением на консоли**.

### Главный результат

Найдено **35 прямых ARM BL к `0x00339AAC`**, штатному обёрточному механизму создания потока, который вызывает `0x0033A2DC`. Для **34 вызовов** из непосредственной предшествующей инструкции `LDR r3,[pc,...]` восстановлена строка имени потока. Для всех 35 найдено по одному локально загруженному литералу `r1` с адресом точки входа. Один вызов по `0x004CB3C8` пока использует имя, передаваемое иначе (или динамически): неизвестное имя **не выдумываем**.

Статические адреса интерфейса обработки потоков:
- `0x00339AAC`: wrapper, подтверждён по исполняемому коду (использует стек и передаёт параметры через `0x0033A2DC`);
- `0x0033A2DC`: внутренний механизм создания; детали параметров и RTOS-контекст уточняются;
- `0x00280810`: создание `Demo GUI`, вход `0x003BE5B0`;
- `0x00447610`: создание `Systen initial Thread`, вход `0x00447540`;
- `0x0044749C`: создание `Systen BackGround Thread`, вход `0x004473BC`.

## Строго подтверждённая начальная цепочка

```text
MMI 0x00280040 (ARM start, CP15, векторы, стеки, BSS)
  |-- BL 0x00299C90  (сброс/синхронизация кэш-подсистемы, видно CP15)
  |-- BL 0x002976D0  (условный вызов через табличный указатель)
  |-- BL 0x00299A98  (обход диапазона указателей / диспетчер инициализации)
  `-- BL 0x00297CE8  (startup)
       |-- BL 0x00297D04  (BX LR, noop)
       |-- BL 0x00297D08  (BX LR, noop)
       |-- BL 0x002807C8  (конструктор Demo GUI)
       |    `-- BL 0x00339AAC (поток: r1=0x003BE5B0, priority 25, stack=0x4000)
       `-- BL 0x0033C0FC (следующий RTOS этап; точное назначение не доказано)

Demo GUI 0x003BE5B0
  `-- BL 0x00447640 (координатор системной инициализации)
       `-- BL 0x004475C0 (создаёт `Systen initial Thread`)
            `-- BL 0x00339AAC (entry r1=0x00447540)
```

**Важно:** стрелки `BL` доказаны декодированием машинных инструкций, но некоторые вызовы могут проходить по условным ветвям. Создание потока не означает, что он уже исполнился в этот момент. Два ребра, показывающие начальную функцию потока, имеют основание в статических литералах `r1` и должны интерпретироваться как *передача адреса*, а не прямой `BL`.

## Что это меняет в проекте SPMP-OS

**Реальный следующий шаг для модернизации штатной системы** — восстановить код `0x003BE5B0`, `0x00447540`, `0x004473BC` и интерфейс сообщений между ними. После этого можно определить, какую часть GUI допустимо заменить, используя существующую eCos и драйверы. Затем создать совместимый нативный модуль, запускаемый только из штатной MMI, без замены заводского RAP/RedBoot.

**Для независимой SPMP-OS** необходима отдельная работа: исправная карта RAM, инициализация исключений/IRQ, планировщик, управление SD/LCD/кнопками/PCM, проверенный контроль передачи управления из RAM. При наличии таблицы потоков легче понять порядок служб и аппаратных драйверов, но сама она не заменяет ядро.

### Важные ограничения

1. OEM MMI очищает ориентировочный диапазон `0x0056AD90`–`0x006C8FDC` при старте. Нельзя размещать там буфер межстадийной передачи без проверки.
2. Название `watchdog_handle` в MMI не доказывает работу аппаратного watchdog на стадии RedBoot или после падения ядра.
3. `0x0033C0FC` может передавать управление дальнейшему RTOS запуску, но его назначение ещё не установлено полностью. Нет оснований выпускать готовый патч MMI только по обнаружению этого вызова.
4. 35 — число **прямых вызовов конкретного wrapper**, а не полное число когда-либо существующих потоков: потоки могут создаваться динамически или через иные интерфейсы.
5. `ghidra_scripts/SPMP_InspectThreadEntries.java` содержит список 34 распознанных адресов. По умолчанию `APPLY_RENAMES=false`, он **не меняет проект**. Для переименования только внутри Ghidra (не бинарника) явно изменяется флаг. Runtime Java-скрипта здесь не проверен, поскольку Ghidra отсутствует.

## Повторить анализ

```sh
python3 tools/trace_mmi_threads.py --rap 8000_MMI.RAP --output evidence
python3 -m unittest discover -s tests -v
```

Если оригинал отличается по SHA-256, анализатор откажется работать: перенос абсолютных ARM-адресов на другую сборку без проверки опасен. Приложение не содержит файлов, записываемых в память консоли, и ничего не прошивает.

## Дополнительная находка — пробелы в имеющемся прогоне Ghidra

Все **35 адресов точек входа** начинаются с характерного ARM-пролога `MOV R12, SP` (машинное слово `0xE1A0C00D`). При сопоставлении со списком **только автоматических имён `FUN_...`**, извлечённым из GZF на Stage 53, совпали **5 адресов**, а **30 не найдены в этом индексе**. Это **не** доказывает, что Ghidra не создала соответствующие объекты функций: адреса могли иметь другие имена или оказаться внутри более крупных функций. Но теперь все эти точки стоит проверить в CodeBrowser и при необходимости обозначить функциями с `F`.

См. `evidence/ghidra_entry_prologue_audit.json`. Это особенно важно для декомпиляции `Systen initial Thread 0x00447540`, `Game thread 0x00460AB0` и `Power management thread 0x002E2120`: эти адреса имеют валидный ARM-пролог, но не встречаются среди автоматически экспортированных `FUN_...`.
