# Stage56 — загрузчик видео/JPEG и CEVA в оригинальном MMI

## Результат

Для точного `8000_MMI.RAP` SHA-256
`5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`
восстановлена цепочка штатного выбора, чтения и загрузки видео/JPEG-модулей.
Это статическая декомпиляция и проверка ARM-инструкций; кодек или MMIO на
консоли не запускались.

```text
media_Start 0x002E1360
  -> video selector 0x0031B588
  -> read triplet 0x0034B1A8
  -> MMPi parser 0x0034A7B8
  -> load triplet 0x0034B400
       OS_EXT parse(mode=0) -> start CEVA -> wait ready
       OS_INT parse(mode=0x10) -> command 81 01 00 00 -> wait
       codec  parse(mode=0x10)
```

`0x0031B588` выбирает тройки `OS_INT`, `OS_EXT`, `codec` для MPEG-4
SP/ASP/HD, MJPEG, H.263, H.264, WMV7/8, VC-1, MPEG-2, DivX3 и RealVideo 8/9.
Штатные пути находятся в `/Rom/Image`. Сначала код пытается открыть резервный
путь `/fat20a2/hda2/xyz`, затем ROM-путь. Это отладочная OEM-схема, а не
рекомендация использовать NAND id2 для пользовательских файлов SPMP-OS.

JPEG-функция `0x00323370` строит относительно каталога три имени:
`/jpgdec_os_ext.img`, `/jpgdec_os_int.img`, `/jpgdec.img`, после чего вызывает
тот же общий загрузчик `0x0034B1A8`/`0x0034B400`. Поэтому JPEG остаётся лучшим
первым изолированным кандидатом для будущего аппаратного теста.

## Восстановленный MMPi-контракт

`0x0034A7B8` поддерживает `MMPi` и сжатую ветку `MMPh`, проходит несколько
`MMPd`, а внутри каждого — заданное число `MMPs`:

| Поле `MMPd` | Смещение | Наблюдаемое значение/смысл |
|---|---:|---|
| record bytes | `+4` | 36 |
| flags | `+16` | например `0x61000200` или `0x61010200` |
| MMPs count | `+20` | число последующих сегментов |
| entry | `+24` | принимается при `(flags & 0xF0000)==0`, кроме `0xFFFFFFFF` |
| CEVA mode | flags `17:16` | передаётся в специальный segment-copy backend |

`MMPs` имеет 24-байтовый заголовок, полную длину по `+4` и destination по
`+8`. Обычная ветка копирует payload непосредственно; ветка mode `0x10`
передаёт payload, destination и `flags[17:16]` в CEVA-oriented copier.

Полный пользовательский архив дал 52 исследованных `MMPi` файла в основном
каталоге и `GAME/KGBVIDEO*`. Все прошли строгий обход границ:
1–4 дескриптора и 13–192 сегмента на файл. Типичная пара flags — mode 0 с
entry `0x00100000` и mode 1 с entry `0xFFFFFFFF`. Это исправляет прежнюю
ошибочную трактовку байтов `0x61` и count как «family/slot».

## Нижний CEVA transport

Цепочка продолжена до `0x0034A62C -> 0x003486B8 -> 0x0034A034`.
Специальный MMPs copier не пишет destination напрямую. Он формирует 20-байтную
команду mailbox:

| Смещение | Наблюдаемое значение |
|---:|---|
| `+0` | opcode `0x90` |
| `+1..3` | `00 10 00` для вызова из MMPi parser |
| `+4` | `mode != 0` |
| `+8` | MMPs destination |
| `+12` | размер payload |
| `+16` | ARM-указатель на payload |

Перед публикацией mailbox штатный код временно маскирует IRQ/FIQ и выполняет
CP15 cache-drain/synchronization sequence. Ответ проверяется по байту `+2`.
Отдельная команда перехода к загрузке кодека — `81 01 00 00`.

Стартовая функция `0x003488F8` записывает entry `OS_EXT` в `0x9053046C`,
обнуляет `0x9053200C`, `0x90532044`, `0x90532804`, `0x90532808` и выполняет
последовательность `0 -> OR 1 -> 0x101` по `0x90530468`. Готовность затем
опрашивается через `0x9053200C`. Это точные обращения оригинала, а не
разрешённая карта MMIO для нового кода.

## Порядок и таймауты

1. Каждая из трёх картинок читается целиком в 64-байтно выровненный буфер;
   выделяется минимум 64 КиБ, даже если файл меньше.
2. `OS_EXT` разбирается с mode argument 0; полученный entry сохраняется.
3. CEVA стартует. Аргумент wait-функции равен 30, но цикл `do/while` выполняет
   до 31 чтения; после каждого чтения следует задержка 10 OEM-единиц.
4. `OS_INT` загружается с mode argument `0x10`.
5. В служебный буфер помещаются байты `81 01 00 00`; второй wait с аргументом
   30 также выполняет до 31 чтения.
6. Последним загружается собственно codec с mode argument `0x10`.

Штатный media path не устанавливает checksum-bit при вызове parser. Поэтому
два checksum-слова `MMPi` нельзя считать проверенной подписью кодека. Новый
`spmp_mmpi_inspect` проверяет все границы/магии/длины, но намеренно не обещает
аутентичность и ничего не загружает.

## Ответ PIU, IRQ и CEVA-команды

Ожидание синхронного ответа находится в `0x0034A124`. В раннем polling-режиме
оно ждёт bit `0x08` регистра `0x9053204C` и подтверждает этот же bit. В штатном
RTOS-режиме функция ждёт event bit 1 с абсолютным deadline `current + 0xBB8`
OEM-единиц времени. Указатель ответа берётся из `0x9053203C`, после чего
оригинал устанавливает в нём alias-bit `0x10000000`. Это наблюдаемое
преобразование адреса, а не доказательство общей карты памяти для SPMP-OS.

Инициализация PIU в `0x0034A3F4` очищает и подтверждает биты `0x38`, разрешает
bit `0x10`, создаёт interrupt vector 31 с priority 12 и пару обработчиков:

- ISR `0x00349F48` читает status, считает события bits `0x08`/`0x10`,
  подтверждает их и возвращает 2 для запуска DSR;
- DSR `0x00349FBC` выставляет event bit 1 ожидающему ответ и будит отдельный
  поток входящих команд;
- поток `dspCmdDispatcher` (`0x0034A2C4`, priority 8, stack 8192) постоянно
  принимает CEVA→ARM команды и направляет opcode в таблицу callbacks.

Таким образом, mailbox двунаправленный: вызов `0x90` имеет синхронный ответ,
но CEVA также самостоятельно вызывает ARM через диспетчер. Для будущего
provider недостаточно скопировать MMIO-записи: нужны единое владение PIU,
cache coherency, безопасное время жизни буферов и сериализация callbacks.

Таблица диспетчера `0x0055B7E0` имеет 256 слотов; в точном образе заполнены
только семь. Входящий запрос начинается с `opcode` по `+0`, флага no-reply по
`+1`, 16-битного размера payload по `+2`, данные начинаются с `+4`:

| Opcode | Handler | Роль по коду и диагностическим строкам |
|---:|---:|---|
| `0x40` | `0x003499F8` | изменение геометрии LCD |
| `0x41` | `0x00349B7C` | запрос scale engine |
| `0x42` | `0x00349974` | очистка/reinit LCD |
| `0x43` | `0x00349CC8` | выделение ARM-памяти для CEVA |
| `0x44` | `0x00349D34` | освобождение ARM-памяти |
| `0x45` | `0x00349DB8` | отладочное сообщение |
| `0x46` | `0x00349E3C` | чтение debug flags |

Указатель команды CEVA→ARM читается из `0x90532040`. Ответный ARM-буфер
публикуется через `0x90532034`: до этого оригинал записывает status/ack bit
`0x02`, сохраняет указатель и выполняет cache clean/write-buffer drain. Называть
bit `0x02` уведомлением пока нельзя. Обратная пара для ARM→CEVA — command pointer `0x90532030` и reply
pointer `0x9053203C`. Особенно важны `0x43/0x44`: CEVA получает адреса ARM
heap, поэтому без точной модели alias/cache/lifetime запуск кодека небезопасен.

## Ограничения и следующий шаг

- Wait-ready читает image-specific `0x9053200C`. Этот адрес нельзя переносить
  в SPMP-OS до проверки платы, карты RAM/MMIO и cache maintenance.
- В оригинале есть условные бесконечные циклы после timeout/null mailbox reply,
  включаемые debug-флагами. Новый provider обязан всегда возвращать ограниченную
  ошибку и не копировать это поведение.
- Значение временной единицы задержки и точное значение состояний ready пока
  требуют восстановления нижнего CEVA driver. Число `0xBB8` зафиксировано,
  но переводить его в миллисекунды без периода системного tick нельзя.
- Семантика `OS_EXT`/`OS_INT` установлена по порядку загрузки и путям, но не
  означает, что один файл является обычным ARM-кодом.
- Следующий безопасный шаг: восстановить структуры LCD/scale callbacks,
  значения ready-state, границы mailbox buffers и точную семантику CP15
  cache ops, затем описать ownership ABI.
- Только после этого можно подготовить MMI-hosted JPEG probe с таймаутом и
  обычным возвратом; исполнять его без аппаратной проверки адресов нельзя.
