# SPMP-OS Stage 34 — RAM Boot Gate + read-only HAL + двухпанельный каталог

**Дата:** 11.11.2026
**Платформа:** Sunplus SPMP8000 / Defender MultiMix Magic, ARM926EJ-S / ARMv5TE (аппаратная ревизия пока не проверена).
**Тип:** исходники, host-тесты и ARMv5 EABI5 **ET_REL объект**. **НЕ готовая прошивка, НЕ запускаемый ELF/BIN/RAP.**

## Что реально изменилось

### 1. `spmp_boot_gate`

Новый ABI-независимый интерфейс валидирует предоставленную платформой карту RAM, границы `module_slot` и зарезервированные системные участки, а затем без записи в память проводит аудит ARM ELF32 ET_REL через существующий Stage10 loader. Внутри нет ни одного фиксированного *реального* адреса Defender, MMIO, NAND, USB/ISP или команды RedBoot.

`spmp_boot_stage` — **не самостоятельный загрузчик устройства**, а входная точка для будущего проверенного штатного RAM-сервиса. Он:

- Проверяет ELF и план релокаций **до** запроса доступа к оперативной памяти.
- Вызывает платформенный `confirm_slot_owned` для именно этого участка, затем `map_slot`; никакие адреса не превращаются непосредственно в C-указатели.
- Отказывает при перекрытии исходного ELF и целевого RAM-слота.
- Требует **успешного** завершения обеих операций `clean_dcache` и `invalidate_icache`.
- При неуспехе кэша затирает только записанную часть подтверждённого слота, сбрасывает `staged`/`cache_confirmed`; **не** вызывает функцию входа ELF.
- На любой ошибке очищает структуру результата, чтобы не осталось устаревшего флага готовности.

Без отдельно реализованного и аппаратно подтверждённого `spmp_boot_platform` вызвать эту функцию на консоли **нельзя**. Подмена флагов подтверждения данными из чужого RedBoot несёт риск повреждения RAM текущей ОС.

### 2. `spmp_diag_hal`

Протокол **исключительно чтения**: кнопки, монотонные миллисекунды, наличие SD, разрешение LCD и параметры звука. Все вызовы делаются через заранее привязанные функции eCos/HAL. Неизвестные функции, адреса периферии и драйверы не выдуманы. Отсутствующие данные помечаются как недоступные.

### 3. `spmp_ro_fs` — первый рабочий слой файлового менеджера

Два независимых состояния панелей, выбор активной панели, страницы каталога до 64 записей, абсолютные пути, защита от `..`, корневая папка, счётчики **всего записей/файлов**, размер выбранного файла (uint64) и FAT-дата `ДД.ММ.ГГ`. UTF-8 имена остаются текстом для рендера системными шрифтами. API не содержит методов записи, копирования, удаления или изменения файлов. Ресурсоёмкий временный список передаётся вызывающей стороной, а не создаётся на маленьком стеке ARM-задачи.

**Не сделано пока:** реальное подключение `fatfs_*`, экранная клавиатура, txt/log-редактор, копирование/перемещение/переименование/удаление, полноценная отрисовка окон менеджера на устройстве.

## Сборка и тестирование

```
make stage34-check
make stage34-arm
nm -u build/spmp_stage34_ram_gate_armv5.o
readelf -h -A build/spmp_stage34_ram_gate_armv5.o
```

- ARM объект `build/spmp_stage34_ram_gate_armv5.o`: **ET_REL, ARM EABI5, ARMv5TE, soft-float**; `nm -u`: 0 импортов; нет final link и установленного entry point.
- Mock RAM Boot Gate: 12 негативных схем, 20 000 псевдослучайных схем, защита от alias, отсутствие вызовов до preflight, проверки очистки при неудачном cache callback, canary: PASS.
- Mock HAL/FS: пять read-only probes, два состояния панелей, каталог 150 записей / 148 файлов, страницы 64+22, короткая дата, запрет traversal и ошибки без повреждения панели: PASS.
- `-fsanitize=address,undefined` на обоих новых host harness: PASS.
- Старые `overlay-tests`, `memory-tests`, `stage31-check`, `stage32-check`, `stage33` regression: PASS.
- Все 34 темы v9, два режима отрисовки и тесты графики: PASS.

Числовые RAM-адреса в `tests/loader/stage34_boot_harness.c` **выдуманы только для теста**. Их строго запрещено переносить в конфигурацию устройства.

## Непроверенные аппаратные параметры

1. Установить реальную плату/ревизию, фактический объём RAM и зарезервированные участки FSP, RedBoot, LCD/DMA.
2. Подтвердить точную семантику native launcher, которому можно доверить предоставление свободного RAM-слота и возвращение управления.
3. Установить карту системных `fatfs_*`, LCD, PCM и клавиш (только после анализа конкретного firmware/dump).
4. Согласовать invalidate/clean I-cache/D-cache на конкретном ARM926 в используемом режиме MMU и с FSP scheduler.
5. Провести эксперимент на железе **только через проверенный не-FLASH путь** и с подготовленным восстановлением.

См. `docs/STAGE34_DEVICE_RESEARCH_CHECKLIST_RU.md`.

## Не делать

- Не переименовывать `.o` в `.bin`/`.rap`, не запускать его на консоли.
- Не прошивать RedBoot, NAND или заводской FSP на основании host-тестов.
- Не использовать тестовые адреса `0x4000xxxx`, `0x8000xxxx`, `0x00030040`, взятые из чужих дампов, как карту RAM Defender.
