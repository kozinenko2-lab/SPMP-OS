# SPMP-OS CodecLab v3 — ARMv5 / Sunplus stock reverse engineering

## 1. Исследованная прошивка

Исследованы оригинальные пользовательские `LIB*.O` из `Defender_MultiMix_FSP_All_Extracted.zip`. Исходный FSP не переписывался; закрытые бинарники НЕ включены в этот пакет. Сверку контрольных сумм, внешних вызовов и числа функций см. `reports/stock_codecs_v3.json`. Переисследование запускается `python3 tools/audit_legacy_objects.py --folder <извлечённые_файлы>` (утилита читает только файлы и запускает `readelf`).

Тип исходных `.O`: little-endian ARM32 `ET_REL`, старые флаги `0x200` (GNU EABI/software FP), большинство имён функций `GLOBAL HIDDEN`. Таблицы перемещений: `R_ARM_ABS32`, `R_ARM_CALL`, `R_ARM_JUMP24`. В `.O` практически нет прямых зависимостей от драйверов или libc; большинство внешних вызовов приходятся на арифметику EABI (`__aeabi_*divmod`) и слабый `Lib$$Request$$armlib`. Это не доказывает совместимости или самостоятельной работоспособности декодера: приложения передают контекст, потоки, буферы и другие данные по непродокументированному ABI.

### 1.1. Реальные признаки интерфейса MP3

- `mp3_decoder_working_ram` (`.text+0x0000`) использует `r0` как входной объём, `r1`,`r2` как указатели на результаты. Доступные режимы: >=18432 → 300/18176; >=8192 → 11564/6912; >=4608 → 13868/4608; меньше → 18476/0. Единицы и назначение двух выходов требуют аппаратной проверки. В `spmp_stock_mp3_working_ram_recovered()` восстановлена **логика запроса**, а не полный MP3-декодер.
- `mp3_decoder_init` (`.text+0x0058`) получает несколько аргументов в `r0..r3`, выравнивает контекст по 8 байтам и размещает указатели по смещениям, в том числе `+0x74`, `+0x78`, `+0x84`, `+0x88`, `+0x7c`, `+0x80`. Значения зависят от режима памяти.
- `mp3_decoder_run` (`.text+0x0230`) использует `r0` как указатель на выравниваемый контекст, сохраняет `r1` по `+0x1c`, `r2` по `+0x58` и использует семиступенчатый автомат по байту `+0x42`. Он генерирует блоки 1152 стереосэмплов в одном из путей выполнения. Полный контракт функции и поведение после ошибок неизвестны.
- `mp3_get_sampling_rate` (`.text+0x06f4`) извлекает индекс по `ctx+0x2c` и берёт частоту из таблицы; `mp3_get_bitrate` (`.text+0x06a4`) использует индексы по `ctx+0x28/+0x29/+0x2b`. Эти поля НЕ следует открывать как стабильную структуру в SPMP-OS.

### 1.2. Реальные признаки интерфейса FLAC

- `flac_working_ram_size()` (`.text+0x1624`) возвращает константу `0x58c8`, то есть **22728 байт**. Это статический запрос оригинальной библиотеки, не её фактический верхний предел RAM с приложением.
- `flac_decoder_init` (`.text+0x1928`) получает в `r2` указатель на рабочую область, очищает первые 3784 байта, устанавливает внутренние указатели и сохраняет адрес в `[r0]`. Полный ABI не подтверждён.
- `FLAC__crc8`, `FLAC__crc8_update`, `FLAC__crc8_update_block` используют таблицу. Новая реализация рассчитывает стандартный CRC-8 FLAC алгоритмически и проверяется тестовыми векторами.
- `FLAC__lpc_restore_signal` содержит оптимизированную сборочную логику восстановления линейного предсказания; `flac_decoder_run` имеет проверку одного из внутренних ограничений относительно 19968. Это не означает универсальный лимит размера трека или кадра.

### 1.3. Видео/JPEG

Файлы `H264_CODEC.IMG`, `MPG4ASPDEC.IMG`, `MPG2DEC_CODEC.IMG`, `MJPGDEC.IMG`, `DIVX3DEC.IMG`, `JPGDEC.IMG`, `JPGENC_CODEC.IMG` имеют заголовки `MMPi`, один или несколько дескрипторов `MMPd` длиной 36 байт и цепочки `MMPs` длиной не менее 24 байт. Размер по смещению 4 соответствует длине файла. Stage56 установил поля `MMPd`: flags по `+16`, число `MMPs` по `+20`, entry по `+24`; flags `0x61000200` допускает entry, `0x61010200` использует CEVA mode 1 и entry `0xffffffff`. `spmp_mmpi_inspect` теперь обходит все дескрипторы/сегменты с проверкой границ и сводит entry/mode/payload — НИКОГДА не копирует и не исполняет содержимое. OEM media path вызывает parser без checksum bit, поэтому два слова checksum сохраняются как метаданные, но не объявляются доказательством доверия.

## 2. Новые C-библиотеки вместо прямой привязки закрытого кода

`spmp_flac_lite.c`: реально декодирует стандартные **нативные FLAC** (моно и стерео, поддерживаемые глубины 8/12/16/20/24 бит, константный, verbatim, fixed predictor и LPC, остатки Rice 4/5, left/right/mid-side stereo) в interleaved PCM16, проверяет CRC8/CRC16 и отказывает при повреждениях. Внутри декодера нет `malloc`, float и системных вызовов. Scratch задаётся приложением (`2 × max_block × 4` байта, 4-byte alignment): для `max_block=4096` — 32768 байт, для 4608 — 36864 байта. `spmp_flac_decode_chunk()` поддерживает SD-поток с внешним скользящим буфером, но вызывающий код обязан подавать хотя бы один полный сжатый FLAC-кадр и управлять чтением/буферизацией. Альтернативно доступно декодирование целого буфера `spmp_flac_decode_frame()`.

`spmp_media_probe.c`: MP3 MPEG-1/2/2.5 Layer I/II/III frame header, битрейты, длительность в сэмплах и размер кадра, поиск кадров с подтверждением; AAC ADTS LC-подобные заголовки (профиль, частота, каналы, размер кадра). **НЕ** декодирует MP3/AAC PCM. Восстановлены query-only оригинальные функции памяти, без опасной совместимости `decoder_init/run`.

`tools/relink_stock.py`: на локальных, законно полученных `.O` выполняет опытную *повторную компоновку* (НЕ рекомпиляцию закрытых исходников) `MP3`/`FLAC` через `clang`+`ld.lld` вместе с узким ARMv5 wrapper. Требует локального FSP, бинарники не раздаются. Полученные `.o` не являются готовыми плеерами, не тестировались на плате и могут иметь EABI несовместимости. Оставлять их вне выпущенной прошивки до проверки железа, лицензии и правильных вызовов.

`build/mmpi_inspect <module.IMG>` выполняет тот же безопасный полный обход `MMPd/MMPs` на локальном файле и печатает только сводку. Он не проверяет право распространения, не загружает сегменты и не обращается к CEVA/MMIO.

## 3. Что проверено

- `make check`: C unit tests MP3/ADTS/MMPi/CRC/memory-query, затем 4 FLAC bit-exact испытания с 22050 mono, 32000 stereo, 44100 stereo, 48000 mono, несколько режимов компрессии `ffmpeg`; отдельный 24-bit FLAC→s16, негативный CRC8 и 9 типов обрезки.
- `spmp_flac_decode_chunk()` отдельно декодирует все те же тестовые потоки из вызывающего буфера; байты PCM совпадают с основным путём.
- `make armv5`: собраны relocatable ARMv5TE EABI5 soft-float `.o` и архив `libspmp_codec_armv5.a`.
- `relink_stock.py`: проверена статическая компоновка оригинальных MP3 и FLAC `.O` с новыми query-only обёртками. **Ни одного вызова оригинальных функций на реальной консоли не выполнялось.**

Ограничения: нет Ogg FLAC, нет 32-битного FLAC, нет MP3/AAC PCM, нет проверенного аппаратного DAC/SD/HAL, нет произвольного seek, нет надёжного теста воспроизведения на устройстве. Декодер только 1–2 канала. Предусмотрен отказ при неизвестных профилях вместо молчаливого воспроизведения мусора.

## 4. Следующий оптимизационный этап

1. Получить исходники Helix MP3 (fixed point, ARMv4+), включить его как **опциональный** провайдер, собрать ARMv5 без FPU, проверить MP3 CBR/VBR, ID3 и PCM-разницу, затем сравнить с оригинальным `LIBMP3.O` на плате.
2. Сохранить единое PCM16 output ABI; написать SD/FAT streaming queue и DMA двойную буферизацию, отрегулировать underrun с диагностикой. Ограничить память на плеер.
3. Для FLAC: проверить CRC32/MD5 потока при необходимости и долгие файлы; профилировать fixed LPC/Rice, добавить ускорение bitreader и индексы seek. Результаты по кадрам/sec и проценту CPU измерить на целевой плате, а не ПК.
4. Аналогично AAC: исходники фиксированной точки с подходящей лицензией и реальными ограничениями памяти. WMA/APE/AC3/AMR как отдельные плагины, без обещания их поддержки.
5. Видео/JPEG: восстановить `MMPi/MMPd` loader, memory/MMIO/кэш и подменять только backend, не писать программный H.264 для медленного ARM9, если аппаратный путь существует.

## 5. Как соединять с игровой веткой

Только новый каталог `features/multimedia/codec_lab` плюс независимый receipt `.spmp-patches/spmp-mm-codeclab.json`. Ни один файл `src/cores`, `src/loader`, `Makefile`, `third_party` не заменяется. Используйте установщик из корня архива: `python3 tools/mm_codec_patch.py --target /path/to/SPMP-OS_Stage10 --check`, далее `--apply`, `--verify`, `--remove`. Он проверяет SHA-256 и откажется стирать изменённый файл. На future Stage11/12 патч применим, если сохранены три базовых файла Stage10; это проверка структуры, НЕ доказательство API-совместимости. Настоящий вызов кодека подключается отдельно через `spmp_multimedia_hal.h` только после аппаратных тестов.
