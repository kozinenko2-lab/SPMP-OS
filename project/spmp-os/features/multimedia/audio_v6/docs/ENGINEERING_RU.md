# Audio v6 — инженерный отчёт

11 ноября 2026. Цель: ARMv5TE, little-endian, soft-float, SPMP-OS/Defender MultiMix Magic.

## Состав

- `spmp_mixer_v6.[hc]`: четыре независимых голосовых канала, Q32.32 позиционирование ресэмплера, линейная интерполяция в PCM16, Q8 громкости/панорамы, мастер-громкость, равномерный Q16 fade, насыщение выхода, количественные счётчики ошибок, ring буфер.
- `spmp_mix_mp3_bridge_v6.c`: PCM callback для MP3 Player v4 с атомарным непринятием неполного кадра при недостатке места, определение фактической частоты/каналов, поддержка преобразования mono->stereo при записи в ring.
- `spmp_mix_audio_v5_bridge_v6.c`: непосредственное и **буферизованное** соединение FLAC/WAV/OGG/AMR с Audio v5. FLAC не декодируется в маленькие 256-кадровые блоки: его декодер v5 требует выдачу целого блока. Новый адаптер читает большой блок во внешне выделенную память, а микшер забирает частями.
- `spmp_mix_stage10_v6.c`: целевой контракт HAL аудиовыхода Stage10. Драйвер аппаратного DAC/DMA не реализуется этим пакетом.
- `spmp_wma_asf_v6.c`: потоковый read-only разбор ASF File Properties и Stream Properties, включая metadata и длительность с preroll, ограничение 16 МиБ/4096 объектов; **НЕ WMA-декодер**.
- `tools/stock_codec_probe.py`: автоматический анализ оригинальных ARM ELF WMA/AMR из пользовательской FSP; -r компоновка экспериментов, НЕ реконструкция исходников, НЕ готовый исполняемый декодер. Фирменные бинарники не включены.

## Результаты host-регрессии

- `make host arm check` — 9 групп проверок микшера, 1500 псевдослучайных сценариев, 80 разных длин коротких чтений ASF.
- ASF дополнительно проверен с искусственным неизвестным объектом 13 000 байт в заголовке.
- `make check-sanitizers` — AddressSanitizer и UndefinedBehaviorSanitizer, ошибки не выявлены в покрытых сценариях.
- `make stage10-check STAGE10=<Stage10>` — успешно проверены вызовы audio_open, audio_write_s16, audio_close через настоящий Stage10 header и тестовый драйвер (НЕ аппаратный DAC).
- `make benchmark`: на хосте x86_64 смешано 5 120 000 выходных кадров (2 моно-потока 44.1/22.05 -> 48 кГц). Пример замера: 0,080 с процессорного времени. Это **не** измерение на ARM/Defender. `sizeof(spmix_mixer)` = 4448 байт для x86_64 ABI (размер на ARM может отличаться).
- Архив ARMv5 EABI5 содержит `spmp_mixer_v6.o`, `spmp_wma_asf_v6.o`, `spmp_mix_mp3_bridge_v6.o`. ARMv5 флаг подтверждён через `readelf -A`: `Tag_CPU_arch: v5TE`.

| WAV | Audio v5 | 44.1к stereo, 49 613 кадров | 0.0 |
| FLAC | Audio v5 | 44.1к stereo, 49 613 кадров | 0.0 |
| OGG Vorbis | Tremor/Audio v5 | 44.1к stereo, 49 613 кадров | 0.501 |
| MP3 | libmad/MP3 v4 | 44.1к stereo, 30 870 кадров | 0.185 |

Значительное различие PCM для AMR-NB между библиотеками OpenCORE и FFmpeg в коротком тесте оставлено явным. Это не основание заявлять битовую идентичность или полную совместимость. Нужны AMR speech sample vectors и проверки независимо на устройстве.

Для кратных блочных размеров программа интеграционного теста выдаёт нулевое заполнение в конце PCM-файла. Сэмплы в пределах реального аудиопотока проверены отдельно.

## Выход в аппаратный HAL

Стандартный поток: `read/seek -> decoder -> (optional PCM queue) -> spmix_render -> audio_write_s16 -> HAL DAC/DMA`.

Смешивание **никогда** не должно вызывать SD/FAT или декодер из IRQ. Нужен foreground/task или предварительное заполнение ring буферов. `spmix_render` может вызывать пользовательский `pull` синхронно; приложение обязано не вызывать этот API из ISR, если callback читает носитель.

В текущем исходном Stage10 заголовок `spmp_multimedia_hal.h` содержит **контракт-заглушку**, а не физический audio driver. Без PCM DMA, SD/FAT и pinmux нельзя утверждать запуск на консоли. Не использовать пакет для записи во Flash/NAND. RedBoot не меняется.

## Замечания по памяти и ABI

`spmix_mixer` содержит 4 кэша по 256 кадров и небольшой управляющий контекст, без `malloc`. Внешние кольцевые буферы — память приложения, под выбираемую задержку и число каналов. Для FLAC v5 требуется отдельный compressed workspace (v5 указывал 192+ КиБ) **и** достаточный PCM кэш под целый FLAC-блок. В тесте выделялось 8192 stereo frames (32 КиБ). Для AMR actual decoder heap — память OpenCORE, пока не замерена на ARM.

`ld.lld -m armelf -r` успешно принимает штатные `LIBWMA.O`, `LIBAMRNB.O`, `LIBAMRWB.O`, но лишь переносит **оригинальные машинные инструкции** в новый relocatable ELF; объект не связан с API SPMP-OS и не был выполнен на устройстве. Для WMA потребуются восстановление ABI API/памяти/ASF-пакетов или перенос полностью открытого fixed-point декодера. AMR OpenCORE пока проходит на x86_64 через системные `.so`, которые **не являются ARMv5 кодеками**.

Публикация финальной прошивки с libmad GPL и закрытыми оригинальными объектами требует отдельной лицензирующей экспертизы.
