# SPMP-OS Stage 48 — OEM SD startup: 30 вызовов и диагностический монитор ARMv5

Дата: 13 ноября 2026 года. **Инструменты исследования, не перепрошивка, не RAM-загрузчик, не подключённый аппаратный SD-драйвер.**

## Основа анализа

- Оригинальный `8000_MMI.RAP`: SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.
- Сегмент ARM использует смещение `0x4C` в RAP относительно runtime-базы `0x00280000`.
- По ARM-коду в области `0x002B8000–0x002BD500` найдено **30 прямых BL** на процедуру `0x002B9B78`, отправляющую штатную SD-команду.
- `tools/audit_stage48_init.py` повторяет сканирование по машинным словам, сверяет SHA, вычисляет цель BL и восстанавливает значение r0 из локальных MOV/ADD. Для каждой команды сохраняет формирующие инструкции и полный OEM-word, включая неизвестные управляющие биты.
- Найдены: CMD0×1, CMD8×1, CMD55×2, ACMD41×2, CMD3×1, CMD7×1, CMD13×7, CMD6×1, ACMD6×1, CMD12×7, CMD18×2, CMD25×4. Это **статические места вызова**, не утверждение об исполнении всех путей при каждой загрузке.
- Никакого прямого CMD17 в указанной области для этого отправителя не выявлено. **Возможность косвенных вызовов и других отправителей не исключается.**
- Номера ACMD41 и ACMD6 выведены из индекса и контекста предшествующего CMD55, а не из наблюдения сигнала на карте. Конкретные условия успешной инициализации, регистры clock/pinmux, OCR, DMA, IRQ и CRC **не восстановлены полностью**.

| `0x002BA850` | `0x7087` | 7 | CMD7, выбор карты |

**OEM command word не равен обычному номеру команды**: старшие биты имеют нерасшифрованные параметры, поэтому эти слова нельзя напрямую писать в контроллер из собственного драйвера.

## Что добавлено в исходники

- `include/spmp_stage48_sd_monitor.h` и `src/spmp_stage48_sd_monitor.c`: монитор **уже наблюдаемой** команды с аргументом, словом ответа, статусом контроллера, временем (тиками) и кодом ошибки. Монитор сам не делает никаких SD-операций.
- Отдельные флаги показывают, какие поля получены от стороннего backend. Флаг `HW_CRC_REPORTED_OK` означает заявление backend, не подтверждение аппаратного CRC этим кодом.
- Локальный кольцевой буфер 64 события, счётчики успехов и ошибок, безопасное переполнение, контекстная классификация CMD55→ACMD. При сбое — запись в RAM-журнал Stage43 через `spmp_log_event`; при включении verbose можно записывать успехи.
- Сохранение накопленного RAM-журнала в файл остаётся обязанностью Stage44 **после** монтирования FAT. Сектора из IRQ/callback не записываются; RedBoot/MMI не патчены.
- `Makefile`: тесты на ПК, ASan/UBSan, статический аудит оригинального RAP, ARMv5TE EABI5 soft-float, связка с Stage47.

## Воспроизведение

На ПК с clang, Python 3 и исходниками Stage43/47:

```sh
cd research/redboot_sd_stage48
make test static arm integrate sanitize RAP=/path/to/8000_MMI.RAP
```

Если проект развёрнут вне исходной структуры, задайте `STAGE43` и `STAGE47` в Makefile. Сам RAP в ZIP не дублируется, нужен оригинальный файл пользователя с точным SHA.

Реально пройдено:

- 30 мест вызовов, полный SHA и формирующие инструкции: проверка оригинального RAP.
- 6 unit-тестов Python, включая отказ при изменении ARM-инструкции и хэша.
- 100 000 событий монитора плюс проверка сброса флагов и сохранности RAM-журнала.
- AddressSanitizer + UndefinedBehaviorSanitizer на тестовом C-коде.
- ARMv5TE EABI5 soft-float `spmp_stage48_stage47_integrated_ARMv5.o`: нет неразрешённых символов; **это relocatable object без точки входа**.

## До настоящего двойного запуска и логирования

1. Необходим безопасный ранний SD/MMC backend для конкретной платы, с проверенными clock/pinmux/card-present/CRC/DMA, ограниченными ожиданиями, восстановлением контроллера.
2. Нужна UART/RAM-проверка физического чтения LBA0 и побайтовое сравнение с копией сектора на ПК; сначала только чтение.
3. Нужна подтверждённая область RAM, не очищаемая MMI при переходе RedBoot→MMI, и тестирование сохранения логов после появления FAT.
4. Необходимо доказать factory fallback и recovery на реальном Defender до каких-либо прошивочных модификаций.
5. Отладочные адреса из RAP не являются готовыми драйверными адресами для самостоятельных MMIO операций.

**Статус:** RedBoot/FSP/внутренняя память НЕ изменены; включённых загрузочных логов с настоящей консоли пока нет. Этот этап повышает полноту восстановления OEM и готовность RAM-журналирования, но не снимает аппаратные блокеры.
