# SPMP-OS Stage 49 — ЛОГИРОВАНИЕ MMI ПЕРВЫМ ДЕЛОМ

**Статус:** реальные программные модули и статический анализ оригинала. **Не подготовлена устанавливаемая прошивка; на Defender не тестировалось.**

## Главный вывод по оригинальному 8000_MMI.RAP

Проверен оригинальный `8000_MMI.RAP`, SHA-256:
`5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.

При машинном анализе первого MMPs-сегмента обнаружено:

- `0x00298B64` (файловое смещение `0x0018BB0`) — ARM `BX LR`, то есть **пустой обработчик**.
- К нему ведут **4559 прямых инструкций BL**, в том числе сотни вызовов с подготовленными диагностическими аргументами; статический вызов возвращается без сообщения.
- Непосредственно после этого пустого обработчика, `0x00298B68`, расположена полноценная функция форматирования, которая проверяет глобальный флаг по `0x00514244` (в исходном файловом образе он равен нулю). Это **не доказывает**, что простая замена одной инструкции включит всю диагностику: нужны проверка состояния и настройка sink.
- `/dev/ttydiag` в оригинальном образе по адресу `0x004CFB80` (файловое смещение `0x0024FBCC`), ссылка в `0x0033E5E4` и код работы с устройством около `0x0033E4D4`.
- `/dev/haldiag` по адресу `0x004CFB90`, ссылка в `0x0056A788`.
- FAT fileops `write` находится по адресу `0x00283FC4`, `close` `0x00284108`, а `fsync` `0x00284100` — пустая заглушка.

Все адреса — для **только этого SHA**. Не применять к другой ревизии RAP.

## 1. Первый тест — отдельная native-программа без модификации MMI

Исследование `libspmp8k` (Ulrich Hecht, 2012):
https://github.com/uli/libspmp8k

Библиотека умеет находить штатные функции `_ecos_open`, `_ecos_write`, `_ecos_close` и `_ecos_read` в работающей прошивке разных SPMP8000. В исходниках проекта также есть `demos/diag/game.c`: он реально открывает и пишет `diag.txt` через OEM API. Это историческое подтверждение подхода, **но не тест на конкретном Defender**.

В этом пакете `native_probe/game.c` — собственная небольшая программа, которая:

1. стартует внутри уже работающей оригинальной MMI, вызывает `libgame_init()`;
2. открывает для чтения **точный** файл-маркер `SPMPOS.ID` на выбранном SD-монте;
3. побайтно проверяет строку `SPMP-OS-SD-LOGGING-PROBE-V1\n`;
4. **только после успешной проверки** создаёт/дописывает `MMIPROB.LOG`, закрывает файл, выходит;
5. при любой ошибке не делает записи.

Для установки маркера на выбранную FAT-карту скопировать файл `SDCARD/SPMPOS.ID` **в корень карты**.

По умолчанию путь файла в OEM: `/fat20a0/hda1/MMIPROB.LOG`. **ВАЖНО: физическое соответствие `/fat20a0/hda1` съёмной SD на данном Defender пока не подтверждено.** Перед запуском сначала проверить этот mount в штатной системе. Если у данной ревизии SD смонтирована иначе, изменить `SPMP_PROBE_SD_MOUNT` при сборке и перепроверить по диагностике. Файл-маркер снижает риск, но сам по себе не подтверждает физический тип носителя.

**Компиляция native `.bin`:** использовать оригинальную сборку `https://github.com/uli/libspmp8k` и его SDK/toolchain. Переместить каталог `native_probe/` в `libspmp8k/demos/mmilogprobe/` и вызвать `make`. Альтернатива — задать `LIBSPMP8K` как путь к корню SDK в Makefile. В этой рабочей среде **нет верифицированного оригинального SPMP8K SDK и его `libgame.a`, поэтому исполняемый `mmilogprobe.bin` не собран**. Сборка C-проекта проверена лишь синтаксически для ARMv5 по совместимому описанию ABI. Не пытайтесь запустить промежуточный `.o` как программу.

**Результат первого аппаратного теста** — запись `MMIPROB.LOG`. Это подтвердит только доступ из *уже загруженной* MMI. Это ещё **не журнал запуска**.

## 2. Подготовленный RAM-логгер для будущего MMI boot trace

`include/spmp_mmi49_logger.h` + `src/spmp_mmi49_logger.c`:

- 8192-байтный фиксированный буфер, без `malloc`, без прямого MMIO, без записи из диагностического обработчика;
- запись в файл только после callback `sd_ready` **с проверкой физически выбранной SD и маркера**;
- максимальная порция 512 байт; после неё закрываем файл и проверяем результат;
- повреждение SD, ошибка открытия/частичной записи/закрытия не делает прогресс подтверждённым;
- `fsync` не используется: в OEM RAP он ничего не делает;
- только явный разрешённый путь `/fat20aN/hdaN/...`; никаких relative path, `/Rom/...`, `..`;
- при переполнении буфера новые байты теряются и учитываются счётчиком `dropped`, исходная MMI не блокируется;
- для корректного функционирования нужен **проверенный OEM FS backend и сериализация записи/считывания буфера**; на текущем этапе их прямое подключение к конкретной прошивке не сделано.

Доступность RAM-буфера до инициализации eCos и точки включения диагностического tap ещё предстоит проверить. Сигнатура `diag_printf` может оказаться variadic; замена её на произвольный `putc` без адаптации ABI запрещена. Готовой patch-RAP на этом этапе нет.

## 3. Протокол внедрения, чтобы не «убить» консоль

1. Оставить RedBoot и заводскую MMI в исходном виде; отдельно скопировать оригинальные образы и проверить способ заводского восстановления.
2. Проверить OEM SD file I/O standalone native-программой, запущенной из штатной MMI. Проверить файл на карте с ПК.
3. Только после подтверждения файлового пути — исследовать вызовы no-op логгера `0x298B64` и предложить **запускаемую из RAM тестовую копию MMI**, если OEM загрузчик это безопасно поддерживает.
4. Вывод сообщений: сначала RAM, затем файловая подсистема. Не вызывать FAT из прерываний/`putc`.
5. После подтверждения на устройстве — опциональный патч только MMI с включением/отключением, но только при гарантированно рабочем откате.
6. RedBoot не менять.

**Предупреждение:** повреждённый RAP, если записать его в неподлежащий восстановлению раздел внутренней Flash, также может сделать устройство не загружаемым. То, что RedBoot при этом остаётся нетронутым, не гарантирует лёгкого восстановления без проверенного recovery-пути. Поэтому сейчас **нет никаких файлов для прошивки RedBoot или MMI**.

## 4. Воспроизведение анализа и тестов

```sh
python3 tools/audit_original_rap.py /path/to/8000_MMI.RAP --out evidence/verified_oem_diag_stub.json
python3 -m unittest discover -v tests -p test_original_audit.py
make CLANG=clang
```

`make` запускает host-тест, ASan/UBSan, ARMv5 EABI5 объект и проверяет синтаксис native-пробы с тестовым ABI-заголовком. Проверка полного native-линкования **не** выполняется. `tools/audit_original_rap.py` строго сверяет оригинальный SHA и **никогда не меняет RAP**.
