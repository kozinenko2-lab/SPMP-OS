# SPMP-OS Stage 45 — доказательная карта ожидания SD и RAM-диагностика

**Дата:** 13.11.2026. **Исследовательская разработка**, не прошивка RedBoot и не образ для установки.

## 1. Действительно исследованные файлы

- `8000_MMI.RAP`, размер 3 284 556 Б, SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.
- Исходники Stage 43/44 с OEM SD и RAM-журналом. Оригинальные файлы не модифицированы.
- Папка `evidence` содержит конкретные ARM-слова и адреса, проверенные неизменяющим анализатором.

## 2. Дополнительно восстановленный участок SD_P430

В OEM-функции `0x002B9A38`:

- `0x002B9B58` — literal `0x92B0B014`. ARM-инструкции `LDR` в `0x002B9A48` и `0x002B9A64` читают слово статуса через этот адрес; `TST r0,r3` сравнивает его с переданной маской.
- `0x002B9A5C` и `0x002B9A60` составляют предел ожидания `49920+80 = 50000`. `BHI` по `0x002B9A7C` срабатывает на `r2>50000`. Тело может пройти 50 001 раз. Это **не 50 секунд и не 50 000 миллисекунд**.
- `0x002B9AD0` проверяет объединённую маску ошибочных битов `0x630`. Далее отдельно разбираются `0x10`, `0x20`, `0x200`, `0x400`.
- При ненулевых ошибочных битах функция возвращает `0x420`; при программном abort-флаге из `0x00555F18` — `0x405` и обнуляет этот флаг.
- **Критичный нюанс:** при исчерпании лимита, если ошибочные биты `0x630` не выставлены, в доступной ветви код возвращает ноль **даже когда бит ожидаемого события не установлен**. Поэтому простой OEM-код возврата `0` не позволяет достоверно утверждать, что SD-команда завершилась.

В `0x002B9B78` (цепочка задания команды) восстановлена следующая последовательность: `STR 0xFFFF` к `0x92B0B014`, затем переданные `r1` и `r0` записываются в вычисленные адреса `0x92B0B00C` и `0x92B0B008`. После этого идёт вызов poll с `0x04`. Другой путь (`0x002B9C74`) опрашивает `0x40` при чтении нескольких слов ответа. **Это описание того, что делает заводской бинарник; оно не разрешает самостоятельно писать в контроллер на консоли.** Точные сигнатуры, семантика регистров и порядок подготовки pinmux/DMA не доказаны.

Проверены четыре прямых BL-вызова `0x002B9A38`: `0x002B9BC4`, `0x002B9C74`, `0x002B9C98`, `0x002BA494`. Все адреса привязаны к оригинальному SHA.

## 3. Новый безопасный программный компонент

- `src/spmp_stage45_sd_poll.c` — **не аппаратный драйвер**, а ограниченный наблюдатель: получает слово статуса только через внешний callback, никогда не читает MMIO сам, не пишет в SD и не переключает режимы контроллера. Раздельно возвращает `REACHED`, `LIMIT`, `STATUS_ERROR`, `READ_ERROR`, `CANCELLED`, `INVALID`. Это сознательно **строже OEM-функции**: при исчерпании выборок возвращает `LIMIT`, а не потенциально вводящий в заблуждение ноль.
- `src/spmp_stage45_trace.c` — отправляет итог опроса в кольцевой RAM-журнал Stage43 **одним событием на опрос**, без файлового IO и рекурсии. В запись попадают маска, количество выборок и последнее слово состояния.
- Сборка Stage45 вместе с исходным RAM-журналом Stage43 и обработчиком log/handoff Stage44 выполнена в единый объект ARMv5 EABI5.
- Все IO callbacks должны быть безопасны по времени, а область памяти журнала должна иметь подтверждённого владельца. При неготовой SD обязательно продолжать штатную загрузку OEM.

## 4. Проверки

- Статический анализ: 41 машинное слово RAP, 4 адреса BL, 6 Python unittest, контроль исходного SHA.
- Host C: 4 020 утверждений, в том числе 50 001 опрос при исчерпании лимита, ошибки статусных битов, отмена, отказ callback.
- Интеграция кольцевого логирования: 2 записи с проверкой уровня, кода события, полей аргументов.
- AddressSanitizer + UBSan: оба C-теста пройдены.
- ARMv5TE EABI5 soft-float: объект `spmp_stage45_stage44_integrated_ARMv5.o` построен, **0 неразрешённых внешних символов**. Это **не самостоятельный исполняемый образ**.
- Stage44: регрессионные 10 028 утверждений пройдены.

## 5. Что остаётся для настоящих логов RedBoot/MMI на SD

1. Найти по штатным исходным бинарникам полностью подтверждённый backend `read_sector` (CMD17, CRC, DMA, согласование clocks/pinmux). На текущем этапе он **не реализован**.
2. Проверить совместимость установленного варианта RedBoot и независимое восстановление заводского загрузчика.
3. Определить допустимую RAM-область, сохраняемую между RedBoot и MMI, либо сначала логировать через UART; без этого первые события могут быть утрачены.
4. После фактического FAT mount безопасно использовать OEM файловый API для сохранения журнала. Stage44 показал: OEM `fsync` — no-op; принудительного физического flush этим не добиться.
5. Только после реального RAM-теста рассматривать изменения MMI, а изменения RedBoot — ещё позже, при гарантированном восстановлении.

**Прошивка, RedBoot, `8000_MMI.RAP` и заводская Flash не изменены. Новых логов с реальной консоли Stage45 пока не получил.**

## 6. Как повторить

При наличии оригинального `8000_MMI.RAP`:

```sh
python3 tools/audit_sd_poll.py /path/to/8000_MMI.RAP --out evidence/stage45_poll_evidence.json
python3 tests/test_sd_static.py /path/to/8000_MMI.RAP
make test sanitize arm integrate
```

Для `make` нужны clang, lld, nm, и соседние каталоги `redboot_sd_stage43` / `redboot_sd_stage44` из полного проекта.
