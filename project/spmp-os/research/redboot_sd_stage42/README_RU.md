# SPMP-OS — Stage 42: RedBoot / SD Dual Boot (read-only FAT boot path)

**Статус:** полностью воспроизводимый исследовательский модуль, **НЕ загрузочный файл для консоли**. Оригинальный RedBoot не изменён; никаких операций записи на NAND/Flash этот комплект не содержит.

## Исходные данные (подтверждено)

- Исходный `Images_RedBoot_201000427.img`, размер **1 021 324 байта**, SHA-256 `bc00123babe27af9af313ec8b19737f2b6fd3c533b901728a4f0112b55c9d108`.
- Образ содержит **5 PRAW-вариантов**: ScanRam v1.0.0.2, v2.0.0.1, v3.0.0.1, v2.0.0.0, v3.0.0.0. Подтверждены машинные слова в точках штатной загрузки для **всех пяти**.
- Оригинальная загрузка: `/Rom/image/8000_mmi.rap` в `0x00A00000`. Семейство ScanRam v1/v2: процедура `0x0004A998`, вызов загрузчика `0x00038F0C` в `0x0004A9C4`; ScanRam v3: процедура `0x000467F4`, вызов `0x00036BF4` в `0x00046818`.
- `8000_MMI.RAP` из оригинального FSP и присланный отдельный `8000_MMI.RAP` **побайтно одинаковы**. SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.
- `CONFIG.DAT` FSP начинается `ACBCSPMP8000`; это не позволяет само по себе выбрать конкретный установленный RedBoot из пяти вариантов.
- Найдены строки `CLK_SD0`, `CLK_SD1`, но наличие рабочего раннего FAT32 SD-драйвера в RedBoot **не подтверждено**. Ядро eCos/RedBoot и консольный драйвер также не тождественны современному Linux `sunplus-mmc`: переносить регистры из Linux нельзя.

## Схема будущей загрузки

```text
Оригинальный RedBoot (остается резервом)
  ├─ принудительный штатный старт -> /Rom/image/8000_mmi.rap
  └─ попытка SD Boot Bridge
       ├─ SD отсутствует или аппаратный таймаут -> restore OEM state -> заводская прошивка
       ├─ FAT16/FAT32, MBR / superfloppy
       ├─ читается ТОЛЬКО SPMPOS/BOOT.PKG
       ├─ пакет: header + CRC32 + board-id + ELF32 ARM
       ├─ проверка Stage34: RAM ownership, segment limits, cache operations
       ├─ при любой ошибке до handoff -> заводская прошивка
       └─ при успехе -> SPMP-OS
```

Нынешний `src/spmp_fat_reader.c` реализует **только слой FAT**. Он не знает, где находится SD-контроллер, не трогает MMIO, флеш-память или загрузочный блок. На вход требуется подтверждённый аппаратный callback `read_sector(lba, buf512)` с аппаратным таймаутом (и известной ёмкостью карты).

`src/spmp_fat_bridge.c` соединяет его с `read_package` интерфейса Stage41. Сам Stage41 (`src/spmp_dualboot.c`) обязательно возвращает управление заводскому загрузочному пути при отсутствии/ошибке карты или некорректном ELF, при отказе RAM stage, а также при возврате из экспериментальной `jump_sd`.

### Ограничения и защита

1. Поддерживаются только **FAT16 и FAT32**, блок 512 байт, короткие FAT 8.3 имена: `SPMPOS/BOOT.PKG`. FAT12/exFAT/NTFS и LFN-имена не поддерживаются.
2. Корректный MBR или superfloppy; проверка BPB, кластеров, границ устройства и объёма ФАТ. Запрещены записи на SD, включая FAT, журнал и FSInfo.
3. Цепочки кластеров должны завершаться EOC точно в конце файла: это блокирует циклы и противоречивые размеры. Никаких произвольных путей из пакета не исполняется.
4. Максимальный файл `BOOT.PKG`: 8 МиБ + 48 байт; это **программный верхний предел**, а не доказательство наличия такого объёма RAM у консоли.
5. Действует лимит вызовов `read_sector` (параметр `max_reads`). **Принципиально важно:** он не заменяет аппаратный таймаут, если сам драйвер завис внутри вызова.
6. При сбое префикс уже прочитанных данных в RAM зануляется, `*actual` возвращается нулём.
7. CRC32 — контроль случайных ошибок, не криптографическая подпись. Реально безопасная загрузка от злоумышленного образа потребует подписи и независимого доверенного ключа.
8. После передачи управления зависание уже запущенной SPMP-OS не может быть обработано обычным программным возвратом. Для этого требуются подтверждённый аппаратный watchdog, механизм запоминания неудачного старта **либо** принудительная заводская загрузка / извлечение SD при перезагрузке.

### Что написано и собрано

- `src/spmp_fat_reader.c`, `include/spmp_fat_reader.h`: read-only FAT16/FAT32 в freestanding C11;
- `src/spmp_fat_bridge.c`, `include/spmp_fat_bridge.h`: связывание с Stage41;
- `src/spmp_dualboot.c`: логика выбора с fallback из Stage41;
- `src/spmp_dualboot_stage34.c`: контракт RAM gate, аппаратный адаптер не предоставлен;
- `tools/verify_boot_sites.py`: строго сверяет **15 ARM-инструкций и 10 литералов** в точках фабричной загрузки из оригинального RedBoot IMG по SHA-256; **только чтение, не создаёт патч**;
- `tools/scan_redboot_original.py`: общий сканер оригинального PRAW;
- `evidence/*.json`: адреса и хеши оригинальных образов;
- `tests/`: FAT16, FAT32, MBR, фрагментация, циклы, нарушения лимитов, ошибки чтения, mutation tests, связка с factory fallback;
- `build/SPMP_Stage42_SDReader_BootBridge_ARMv5.o`: ARMv5TE EABI5 freestanding **перемещаемый объектный файл** без внешних символов после привязки `spmp_minilibc.c`, `spmp_numeric.c` из Stage40. НЕ запускаемый ELF и НЕ файл для Flash.

## Что надо сделать для загрузки на настоящей плате

1. По read-only UART/version/boot log/дампу определить выбранный из пяти PRAW-вариантов. Имеющийся универсальный образ не говорит сам по себе, какой был прошит.
2. Из original `8000_MMI.RAP`/OEM драйверов восстановить ранний SDMMC-блок (pinmux, clocks, sector I/O) и реализовать жесткие таймауты всех команд, без зависания при отсутствующей SD.
3. Подтвердить свободную область RAM, включая защиту загрузки заводского RAP по `0x00A00000`, и кэширование ARM926EJ-S.
4. Проверить **без записи NAND** загрузку этапа из RAM и штатный ROMFS factory boot после его ошибки.
5. Проверить независимое recovery/NAND backup и forced-factory путь для зависаний. Только потом принимать решение о модификации bootcfg/ROMFS/RedBoot.

**НЕ ПЫТАЙТЕСЬ ПРОШИВАТЬ** `.img` из исследований, `.o`, ZIP или `BOOT.PKG`. Нынешний Stage42 — НЕ готовый dual-boot загрузчик для Defender.
