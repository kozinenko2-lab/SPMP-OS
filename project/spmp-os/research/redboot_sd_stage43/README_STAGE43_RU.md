# SPMP-OS Stage 43 — SD_P430 исследование и журнал загрузки RedBoot/MMI

**Версия:** исследовательский комплект, 13.11.2026. **НЕ устанавливаемая прошивка.** Никаких бинарных патчей RedBoot или `8000_MMI.RAP` не выполнялось. Никаких прямых записей в MMIO, NAND или сырой FAT нет.

## 1. Исходные бинарники, проверенные статически

- `Images_RedBoot_201000427.img`: SHA-256 `bc00123babe27af9af313ec8b19737f2b6fd3c533b901728a4f0112b55c9d108`; 5 вариантов PRAW.
- Оригинальный `8000_MMI.RAP`: SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`, размер 3,284,556 байт.
- Stage42: read-only FAT16/FAT32, `SPMPOS/BOOT.PKG`, SD-first -> штатная ROMFS при отказе.

## 2. Новая находка: реальный драйвер SD_P430

В `8000_MMI.RAP` обнаружен блок диагностики `SD_P430.c` (файловое смещение `0x25765C`, RAM-адрес строки `0x004D7610`). Десятки ARM-вызовов в `0x002B9000–0x002BD800` ссылаются на сообщения SD, например `[SD]::%s(%d)`, `fail to stop SD ctler`, `dump SD Cardinfo`.

Проверяемый анализатор `tools/analyze_oem_sd.py` находит 608 загрузок литералов `ldr ..., [pc, #offset]` в выбранном кодовом окне, включая четыре высоко повторяющихся адреса **кандидатов MMIO**: `0x92B0B010`, `0x92B0B014`, `0x92B0B018`, `0x92B0B01C`. Они похожи на адреса регистров SD-контроллера, но **в этом этапе их регистровые назначения, порядок и возможность безопасной записи НЕ подтверждены**. Следовательно, нет реализации раннего контроллера, которую можно запустить на железе. Не переносите регистры из современного Linux `sunplus-mmc` (у него другой SoC).

В `evidence/` находятся `sd_p430_static_map.json`, `sd_p430_string_xrefs.csv`, `sd_p430_mmio_candidates.csv` с абсолютными PC, адресами literal pool и точными машинными словами ARM. Результат привязан к конкретному SHA исходного RAP, чужие/изменённые версии отклоняются.

## 3. Что реализовано в исходниках

| Файл | Функция | Ограничение |
|---|---|---|
| `src/spmp_bootlog.c` | Временной RAM ring из 256 записей; seq/tick/этап/уровень/событие/аргументы/текст, checksum, обработка переполнения | не сохраняется после обесточивания; требует гарантированной RAM и сериализованных вызовов |
| `src/spmp_trace_bridge.c` | Обёртка событий Stage42: выбор системы, чтение пакета, проверка RAM, stage/cache, возврат к ROMFS | работает после подключения к проверенному boot entry, не патчит RedBoot |
| `src/spmp_sd_trace.c` | Пассивное логирование чтений FAT по LBA (тайминг, статус, частота выборки); **только read_sector** | не реализует SD/MMC командный драйвер |
| `src/spmp_mmi_trace_store.c` | Сохранение в `SPMPOS/LOGS/XXXXXXXX.LOG` через внешние `open_append/write/sync/close` после монтирования SD; продолжение после временных ошибок | не подключён к OEM FAT API бинарника MMI, нужен проверенный файловый адаптер |
| `tools/analyze_oem_sd.py` | Неизменяющий исходники SD_P430 анализ | статический анализ, не железный тест |

Для логов RedBoot доступны **две безопасные выходные ветки**: (а) передавать строки уже существующему UART `putc` и параллельно в `spmp_log_console_char()`, (б) складывать численные события в `spmp_log_event()` и передать буфер MMI. Вторая ветка станет рабочей **только после** подтверждения разделяемого участка памяти, который не затирает reset-код `8000_MMI.RAP`.

После `fatfs_mount` MMI может вызвать `spmp_mmi_trace_flush()`, чтобы записать журнал на SD через **официальный OEM API записи** с ограниченным временем ожидания. Это не реализовано бинарным патчем: точные сигнатуры OEM write/sync и место безопасного hook ещё предстоит подтвердить. Если MMI не достигнет монтирования SD, журнал на карту не попадёт; для таких сбоев нужен UART или проверенный ранний контроллер с записью.

### Формат записи

```
SPMPTRACE v1 session=12345678 count=3 dropped=0
seq=1 tick=0x0000000a phase=1 lvl=1 event=0x00430001 a=0x00000000 b=0x00000000 msg=RedBoot started
seq=2 tick=0x00000014 phase=2 lvl=0 event=0x00430201 a=0x00000000 b=0x00000003 msg=read-sector OK
seq=3 tick=0x0000001e phase=3 lvl=1 event=0x00430100 a=0x00000000 b=0x00000000 msg=MMI entry
```

`tick` — единица платформенного монотонного счётчика, частота **не определяется** самим логгером. Время RTC можно добавлять уже после MMI init. Пара `(session, seq)` служит для дедупликации при повторах записи. Файл формата 8.3, папку `SPMPOS/LOGS` нужно заранее создать на карте. Для имён требуется неповторяющийся номер загрузки или иной проверенный источник ID; переполнение счётчика и повтор ID могут привести к объединению сеансов в одном файле.

### Рекомендуемая подробность трассировки

**RedBoot:** reset, CPU mode, clock, выбор ScanRam-варианта, ROMFS lookup, проверка ключа forced-factory, детект SD, timeout и коды MMC CMD/ACMD, CID/CSD/OCR/RCA (только после безопасного восстановления API), каждый сектор по LBA в подробном режиме, FAT/BPB, CRC BOOT.PKG, RAM layout, ELF segments, cache sync, выбор OEM или SPMP-OS.

**8000_MMI.RAP:** entry/CP15/IRQ, DDR/heap, eCos threads, устройство SD, `fatfs_mount`, FS mount result, часы, кнопки, LCD init, размер и stride видеобуфера, PCM init, списки модулей, загрузка меню XML, MicroWindows, игровые ядра и обработчики ошибок. Не выводить секреты, полный контент секторов, личные данные пользователя или ключи.

События нельзя напрямую писать в файл из прерываний и из `putc` в процессе файловых операций: это вызывает рекурсию и риск зависания. RAM ring должен работать без выделений памяти и без системных вызовов. Сброс лучше запускать из отдельной задачи MMI раз в N сообщений, при важных переходах и при штатном завершении, с ограничением по времени, объёму, и проверкой writable SD.

## 4. Подтверждённые тесты

- Host С11 + строгий `-Wall -Wextra -Werror`: тесты кольца, повреждения, переполнения, консольного putc, успешной и ошибочной загрузки, forced-factory.
- Сохранение после FAT: mount not ready, 8.3 путь, append, sync, отказ записи, повторная попытка, отсутствие потери курсора после ошибки.
- Секторные логи: все запросы / только ошибки, LBA, монотонные тики, ошибочный backend.
- Все три C-теста пройдены с AddressSanitizer + UndefinedBehaviorSanitizer.
- Регрессии Stage42 FAT: 322/322.
- ARMv5TE EABI5 soft-float: объект `build/SPMP_Stage43_BootTrace_ARMv5.o` связан со Stage42; неразрешённых внешних символов нет. **Это объектный модуль, НЕ загрузочный ELF**.

## 5. Что нельзя пока делать

- Перезаписывать оригинальный RedBoot или `8000_MMI.RAP` ради трассировки: нет доказанного recovery и карты разделяемой RAM.
- Считать программные тесты подтверждением доступа к SD на ARM926EJ-S.
- Применять `0x92B0B01x` для реальных MMIO-записей без определения всех битов и полярности, таймаутов и состояния pinmux.
- Считать лог на SD доступным до монтирования FAT или после произвольного зависания ОС.

## 6. Следующая инженерная итерация

1. Дизассемблировать функции SD_P430 (примерный диапазон `0x002B9A00–0x002BC900`): команды, прерывания, таймауты, PIO/DMA, reset, секторное чтение. Сначала доказать **только чтение**.
2. Найти реальные функции `fopen/fwrite/fflush/fclose` для штатной SD FAT (сверить ABI ARM и точки вызовов) и контекст безопасного вызова после mount.
3. Установить RAM, который RedBoot и MMI гарантированно сохраняют, либо выбрать альтернативный канал раннего лога (UART). Проверить на железе независимый forced-factory recovery.
4. Постепенно включать хуки OEM debug без рекурсии, начиная с RAM-тестовой загрузки и аппаратных логов.

**Итог:** готова проверенная программная часть диагностики и статическая карта SD-драйвера. Фактическая запись логов штатным RedBoot/MMI на SD пока не подключена — нельзя заявлять обратное.
