# SPMP-OS Stage 47 — интеграция безопасного чтения SD и сверка OEM команд

Дата: 13 ноября 2026. **Это исследовательский комплект, не прошивка и не загрузчик для записи во Flash.**

## Исходный материал

- Оригинальный `8000_MMI.RAP`: 3 284 556 байт, SHA-256 `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.
- В `tools/audit_stage47_sd.py` зафиксированы **37 машинных слов ARM** и **9 прямых BL-вызовов** общего отправителя команд `0x002B9B78`. Каждое слово проверяется относительно реального RAP; без точного SHA анализатор отказывает.
- 2 подтверждённых вызова с командным индексом **CMD18** (многоблочное чтение): `0x002BB014` и `0x002BB774`.
- 4 вызова **CMD25** (многоблочная запись): `0x002BBB38`, `0x002BBB60`, `0x002BC25C`, `0x002BC28C`.
- 3 вызова **CMD12** (остановка передачи): `0x002BAE60`, `0x002BB2A0`, `0x002BBE4C`.
- Индекс команды — только младшие шесть битов собранного значения `r0`. Остальные биты содержат OEM-флаги, назначение которых не восстановлено полностью. Их **нельзя** использовать для аппаратной записи без дополнительного исследования.
- Перед двумя вызовами CMD18 найдено вычисление аргумента с множителем **512** или **1** (`0x002BB00C` и `0x002BB76C`). Оно соответствует адресации SDSC (байты) и SDHC (блоки), но код определения типа карты пока не доказан.
- **Полный CMD17 не восстановлен.** В этой проверенной выборке восстановлены CMD18/25/12. Их нельзя просто подставить вместо CMD17.

## Что написано

`include/spmp_stage47_guarded_fat.h`, `src/spmp_stage47_guarded_fat.c`:

- `spmp47_command_argument`: расчёт аргумента SD-команды по LBA, блоки/байты, строгое обнаружение переполнения.
- `spmp47_guarded_fat_init`: не принимает неполный backend и не оставляет частично инициализированный интерфейс.
- `spmp47_guarded_sector`: подключает проверяемый Stage46 секторный backend к `spmp_fat_io` Stage42; при ошибках не меняет выходной сектор; контролирует повторный вызов; записывает в оперативный журнал Stage43 LBA и код результата.
- `spmp47_read_package`: делает обёртку совместимой с `spmp_db_ops.read_package` Stage41. Политика Stage41 уже выбирает SPMP-OS или заводской запуск, включая отказ от SD по кнопке.

Этот модуль **не содержит** новых регистров, функций управления тактированием, GPIO, DMA, NAND и операций записи. Поиск FAT-файла `SPMPOS/BOOT.PKG` остаётся только для чтения. Интерфейс `spmp46_reader` должен предоставляться **отдельно проверенным** аппаратным backend и включать подтверждение валидного аппаратного CRC, согласованности DMA и завершения передачи. В тестах это имитируется, но не является доказательством аппаратной корректности.

## Проверки

```
cd SPMP-OS_Stage34/research/redboot_sd_stage47
make test static arm sanitize RAP=/путь/к/8000_MMI.RAP
```

- 10 000 детерминированных секторных транзакций: успех, отказ чтения статуса, неполные данные, неверный CRC, неизменяемый целевой буфер при отказе.
- 14 end-to-end сценариев на синтетических FAT16/FAT32 образах: FAT MBR, фрагментация, повреждённая цепочка, отсутствие файла, сбой backend, принудительный заводской запуск, возврат экспериментального entry.
- 7 Python unittest и точная проверка 37 слов оригинального RAP, девяти вызовов.
- AddressSanitizer + UBSan для C-сектора; полная ARMv5TE EABI5 soft-float **relocatable** сборка без неразрешённых символов. Это **не исполняемый образ на консоли**.

## Что остаётся сделать для реальной консоли

1. Подтвердить ревизию именно установленного RedBoot и карту памяти конкретного Defender.
2. Восстановить и проверить ранние SD pinmux/clock/card-present и безопасный DMA (SD_P430 и прошивочный ROMFS API); запретить бесконечные циклы опроса на аппаратном уровне.
3. Проверить чтение LBA0 с UART-логом на реальном устройстве из безопасного RAM-кода; сравнить сектор с эталоном на ПК. Сначала только чтение.
4. Проверить factory fallback при вынутой SD и при ошибках DMA/CRC до любых экспериментов с загрузочной прошивкой.
5. Выделить и проверить RAM handoff для журналов RedBoot -> MMI. Позднейший exporter Stage44 должен использовать настоящий OEM FAT/close. `fsync` в исследованной OEM FAT-заглушке не гарантирует физическую запись.
6. Протестировать независимую recovery-цепочку и watchdog; только после этого можно рассматривать изменение конфигурации загрузки.

**Ни RedBoot, ни `8000_MMI.RAP`, ни заводская Flash в этом этапе не изменены. Реальных логов консоли пока нет.**
