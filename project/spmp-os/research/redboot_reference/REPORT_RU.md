# RedBoot 2010-04-27: исследование пяти PRAW-образов

## Исходные файлы

- `Images_RedBoot_201000427.img` — 1 021 324 байта, SHA-256 `bc00123babe27af9af313ec8b19737f2b6fd3c533b901728a4f0112b55c9d108`.
- `mmm-firmware-v3_FSP.img` — 87 669 920 байт; ранее полученный штатный FSP-файловый образ Defender.
- Анализ локальных файлов проводился исключительно на чтение. Никакие команды на физическом устройстве не выполнялись.

## Установленная структура

Контейнер содержит 5 последовательных записей `PRAW`. Поле uint32 little-endian по смещению +4 каждой записи равно полному размеру записи **минус 16 байт**; значения совпали с расположением последующих записей. Каждый вариант содержит упакованные компоненты `MMPi`, `MMPd`, `MMPs`, ELF-заголовок ARM 32-bit little-endian, RedBoot и ScanRam. По одному корректному ELF-заголовку на PRAW на локальном смещении `0x88`; оставшиеся строки `\x7fELF` относятся к константам/сигнатурам в исполняемом коде и не являются отдельными вложенными ELF. ELF-заголовки внутри PRAW не означают, что далее содержится обычный цельный ELF с корректной таблицей разделов: PRAW упаковывает его по собственным правилам.

| № | Старт в контейнере | Размер, байт | Поле +8 (назначение не подтверждено) | ScanRam | Баннер RedBoot |
|---|---|---:|---|---|---|
| 1 | `0x000000` | 213 580 | `0x8000D000` | v1.0.0.2 | v2_0_28, 17:41:15 |
| 2 | `0x03424C` | 213 588 | `0x8000E000` | v2.0.0.1 | v2_0_28, 17:41:15 |
| 3 | `0x0684A0` | 190 284 | `0x8050A000` | v3.0.0.1 | v2_0_28, 15:36:02 |
| 4 | `0x096BEC` | 213 588 | `0x8000F000` | v2.0.0.0 | v2_0_28, 17:41:15 |
| 5 | `0x0CAE40` | 190 284 | `0x8050C000` | v3.0.0.0 | v2_0_28, 15:36:02 |

Пять вариантов группируются по близости кода: 1/2/4 почти одинаковы, 3/5 почти одинаковы. Это подтверждает различные семейства/настройки загрузчика и ScanRam, но по одним адресам ещё нельзя определять совместимость с конкретной платой.

## Определённые возможности из строк загрузчика

В вариантах присутствуют, в том числе:

```text
RedBoot(tm) bootstrap and debug environment [ROM]
Non-certified release, version v2_0_28 - built ... Apr 27 2010
eCos GDB stubs [via RedBoot]
RedBoot>
[linux boot]
[Fast boot]
[Load romfs]
[Disable USB]
/ Rom/image/8000_mmi.rap    (фактическая строка /Rom/image/8000_mmi.rap)
linux_kernel.rap
Load image from romfs!
bootkernel: booting from 0x%08x
go_with_addr: booting from 0x%08x
Found the image entry point: 0x%x
Too many program headers
Only absolute ELF images supported
*** Abort! Attempt to load ELF data to address: %p which is not in RAM
RedBoot ISP mode is requested
```

Команды, найденные в таблицах строк программы: `load`, `go`, `help`, `version`, `reset`, `bootcfg`, `dump`, `mcopy`, `mcmp`, `mfill`, `cksum`, `mount`, `umount`, `cache`, `ping`, `ip_address`, `iopeek`, `iopoke`. Есть строки о режимах `xmodem`, `ymodem`, `TFTP`, ELF/S-record, а также USB mass storage и vendor-командах `CMD_BYPASS`/`CMD_GO`. Имеется код сетевого контроллера DM9000. **Наличие кода не подтверждает наличие соответствующего оборудования, доступность порта и возможность физически войти в консоль загрузчика.** Не найдено надёжных признаков стандартного FIS; нельзя автоматически применять команды `fis` из универсальных инструкций RedBoot к этой модификации.

Особенно важно, что код упоминает `linux_kernel.rap`, но в исходном FSP-файловом образе Defender строка `linux_kernel.rap` не найдена, а основной модуль `/IMAGE/8000_MMI.RAP` присутствует. Таким образом, Linux-запуск предусмотрен в универсальной ветке RedBoot; его успешность и выбор режима для Defender не проверены.

## Сопоставление с Defender FSP

В `mmm-firmware-v3_FSP.img` нет баннера `RedBoot(tm)`, но в извлечённом `/IMAGE/8000_MMI.RAP` есть `RedBoot_ver=%08x`, `Scanram_ver=%08x`, `getBootConfig` и диагностическое сообщение `warning! target IC is not 8000(eco_e) or 8050`. Это свидетельствует о связи штатного ПО с соответствующим семейством загрузчика, **но не указывает однозначно, какой из пяти образов подходит устройству**. Оригинальный `PRAW`, найденный как подстрока FSP, относится к встроенному программному объекту и не является тем же RedBoot-пакетом (ни баннер, ни размеры не совпадают).

## Происхождение файла

Точное имя `Images_RedBoot_201000427.img` упоминается в инструкции по перепрошивке JXD1000 (опубликована 27 июля 2010 года): https://tech.sina.com.cn/digi/2010-07-27/17531435383.shtml . Загрузчик выбирается через кнопку BOOT в программе FRM.exe **отдельно** от файлового образа основной прошивки. Это подтверждает предназначение файла, но **не** совместимость именно с платой Defender.

## Безопасный план

1. Сохранить нетронутыми оба исходных образа.
2. Получить маркировку CPU, DRAM и NAND, ревизию платы Defender; сопоставить с параметрами ScanRam и `bootcfg`.
3. Проверить наличие низковольтного UART, определить TX/RX/GND и уровень сигналов; сначала только читать выходные сообщения. Не подавать 5 В на непроверенные выводы.
4. Проверить работу оригинального штатного загрузчика и доступность команд `version`, `help`, `bootcfg` (только чтение), не изменяя конфигурацию.
5. Получить поблочную резервную копию NAND/загрузочной области вместе с необходимыми служебными данными, проверить возможность *физического* восстановления.
6. Только после этого разработать маленький исполняемый тест для **RAM**, проверить командный путь `load`/`go` или штатный механизм загрузки `.RAP`.
7. Затем исследовать запуск ядра Linux и отдельный альтернативный лаунчер. До подтверждения совместимости не переписывать RedBoot и не активировать ISP-запись.

**ВНИМАНИЕ:** образы из папки `extracted/` созданы для статического анализа. Это не готовые прошивки Defender. Не подавать их в FRM/ISP и не записывать в NAND.

## Инструмент

`scan_redboot.py` — самостоятельный Python 3 инспектор; читает контейнер, валидирует длины `PRAW`, строит список вариантов, сообщает номера ELF-заголовков и SHA-256, при параметре `--extract` сохраняет исходные PRAW без изменений.
