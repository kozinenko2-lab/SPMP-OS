# Загрузочная цепочка DefenderOS (этап 1)

## Достоверные наблюдения

* Пользовательский `Images_RedBoot_201000427.img` состоит из пяти корректно разделяемых `PRAW`, содержащих ARM ELF-заголовок. Для всех пяти `e_entry` = `0x00030040`. Заголовки описывают несколько `PT_LOAD`, включая диапазоны в низкой RAM и отображение по адресу `0x9d800000`; эти адреса **не гарантируют**, что тот же layout безопасен для пользовательского приложения.
* В PRAW находятся ASCII-строки `linux_kernel.rap`, `8000_mmi.rap`, `bootcfg`, `bootkernel`, `go_with_addr`, `RedBoot>`. Это признаки реализованных путей, а не подтверждение успешного запуска на конкретной Defender.
* Файл `IMAGE/8000_MMI.RAP` из пользовательского FSP начинается с `MMPi`; внутри встречаются `getBootConfig`, `RedBoot_ver=%08x`, `Scanram_ver=%08x`, файло-ориентированные функции `fatfs_*` и виртуальные пути `/fat20a0`, `/fat20a1`, `/fat20a2`.
* Образ RedBoot исторически фигурировал в инструкциях другой консоли (JXD1000); **не считать его совместимым с Defender**.

## Неустановленные параметры

* Содержит ли Flash Defender именно этот вариант RedBoot, доступны ли UART и CLI.
* Сколько у устройства RAM, где находятся безопасные незанятые страницы, какие области зарезервированы системой, допускается ли функция `go` с возвратом.
* Где расположены RedBoot и таблица обновления во Flash; есть ли надёжный путь восстановления NAND.
* Как именно пакуются `.RAP` и как выбирается Linux-загрузка в конкретной аппаратной сборке.

## Два раздельных пути

**Вариант 1, переходный:** нативная утилита в штатной eCos с libspmp8k. Внутри этого приложения можно разработать меню, загрузчик игр, файловый менеджер, вести диагностику железа. Не нужно переписывать RedBoot.

**Вариант 2, независимый:** получить реальный serial boot log и карту памяти, создать ARMv5 RAM-probe, затем микрокернел, и только после этого передавать управление без eCos.

В обоих вариантах разделить `Boot Bridge` и `DefenderOS Core`: ядро интерфейса не обязано знать, кто и как запустил экран/SD.

## Назначение `ram_probe_armv5.o`

Проверка ARM CPU ID, CPSR, CP15 control, SP и LR. Это **ELF relocatable object (`ET_REL`)**, не самостоятельная программа для запуска на устройстве. В нём нет записи в MMIO/NAND, нет взаимодействия с USB и нет изменения состояния MMU. Данные сохраняются в собственном `.data` объекте. Предполагает доступность CP15 и корректный LR у вызывающей стороны. Преждевременное выполнение всё равно может зависнуть.

Не связывать объект по произвольному адресу. Не пользоваться командами записи Flash, `iopoke`, `bootcfg` в режиме изменения и командами ISP. Первое подключение UART — только чтение с проверенным уровнем сигнала.

## Проверки перед запуском в RAM

1. Фото ревизии платы, CPU, RAM, NAND.
2. Проверка рабочего механизма восстановления и полный поблочный дамп NAND, если он доступен, включая служебные данные.
3. Серийная консоль: вывод баннера, доступность RedBoot, безопасное чтение `version`, `help`.
4. Установить границы свободной RAM (не опираться на параметры из чужого PRAW).
5. Проверить calling convention / return-семантику `go` или штатного `BIN` launcher.
6. Только затем создавать релокированный ELF для RAM и проводить тест без записи во Flash.
