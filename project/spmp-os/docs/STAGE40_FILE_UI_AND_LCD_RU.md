# SPMP-OS Stage 40 — RAM-интерфейс файлового менеджера и трасса инициализации LCD

**Статус: исходники, ARMv5 EABI5 ET_REL, host-тесты. Не загрузочный ELF и не прошивка.**

## Что реально реализовано

1. `SPMP-OS_Stage34/src/ui/spmp_stage40_file_ui.c` и `include/spmp_stage40_file_ui.h` — двухпанельное приложение в разрешении **320×240**, работающее в **выделенной вызывающим кодом RAM**. Программный renderer использует **непрозрачные двухбайтные пиксели**, не делает выводов о RGB565, аппаратных адресах, stride или DMA.
2. Переключение панелей, выделение, переход в каталог, возврат к родительскому, переход между страницами (до 64 записей на страницу), счётчик файлов, размер выбранного файла в байтах и FAT-дата формата `ДД.ММ.ГГ`. Имена передаются как UTF-8 в `spmp40_system_font`: шрифт должен быть предоставлен системным UI при будущей интеграции — никакой шрифт в приложении не зашит.
3. Доступ к каталогам только через проверенный callback `spmp_ro_fs` (Stage 34). В коде **нет** функций создания/записи/удаления/переименования. Все результаты должны быть подтверждены `confirm_readonly`; при ошибке чтения остаётся предыдущая панель. Выбор реальных физических кнопок в эту версию не включён — высокоуровневые навигационные действия не предполагают конкретных GPIO-битов.
4. По исходному `8000_MMI.RAP` восстановлено **10 прямых вызовов ARM BL** из инициализации графики и **10 контрольных инструкций** модификации программных дескрипторов. Выводы прилагаются в `evidence/lcd_init_direct_calls.csv` и `lcd_descriptor_instructions.csv`. Пин SHA-256: `5529b173b3fb612b2e7f516af807f1342d24ea6f7101be034e1e0d08fed25c4e`.
5. Уточнение важной константы: ARM-инструкция `0x00312ECC: E3833202` использует rotated immediate **`0x20000000`**, а не `0x00020000`. Это бит *программного* слова дескриптора. Его назначение в аппаратном LCD **не доказано**.

## Использование программного файлового менеджера

Передать свой `spmp_ro_dual_panel` (крупная структура — не помещать на небольшой стек задачи), свой отдельный `spmp_ro_panel` для scratch, `spmp_ro_fs` с подтверждёнными callback'ами, пути обеих панелей. Вызвать `spmp40_init`, затем `spmp40_navigate` при получении логического действия и `spmp40_render` для отрисовки в собственную RAM-поверхность `spmp39_surface16` с шагом строки >= 640 байт. `spmp40_system_font` получает UTF-8 и пиксельный callback с ограничением области вывода. Цвета — предоставленные вызывающим кодом *двухбайтные токены*, формат зависит от будущей проверки LCD на плате.

Текущая реализация **не вызывает** `present()` и не передаёт пиксели дисплею. Встраивание в штатное LCD-окружение, верификация структуры framebuffer, физические кнопки, файлы с правом записи, текстовый редактор и экранная клавиатура — отдельные задачи.

## Повторная сборка и тесты

После распаковки ZIP с каталогами `SPMP-OS_Stage34` и `research`:

```bash
cd SPMP-OS_Stage34
make stage40-ui-test stage40-arm
make stage40-verify SPMP_RAP_PATH=/путь/к/8000_MMI.RAP
readelf -h build/spmp_stage40_readonly_ui_armv5.o
nm -u build/spmp_stage40_readonly_ui_armv5.o
```

Отдельно Python-трасса:

```bash
python3 research/oem_abi_stage40/tools/trace_lcd_init.py --rap /путь/к/8000_MMI.RAP --out /tmp/spmp40_evidence
```

Скрипт строго сверяет SHA-256 исходного RAP. При несовпадении выводит ошибку вместо попытки перенести адреса на другую прошивку.

Результат компоновки — **ELF32 ARM ET_REL, EABI5, soft-float**, без внешних символов благодаря Stage 29 `spmp_minilibc`. Это НЕ исполняемый загрузчик. Не записывать в Flash и не пробовать запуск на неизвестном RAM-адресе.

## Что не восстановлено

Достоверное название LCD-регистров `0x93000054/84/78`, полная последовательность питания и reset панели, значение pixel format, реальный pitch, владение DMA/SDRAM, проверенный framebuffer, совместимый системный font ABI, безопасные callback'и платформы. Новое наблюдение относится к **программным** функциям инициализации, а не к завершённому физическому драйверу.

## Риски и границы

- `8000_MMI.RAP` не включён в распространяемые архивы; для повторной проверки используется собственный оригинальный образ.
- Графическая RAM принадлежит вызывающему коду. Передавать MMIO-указатель вместо RAM небезопасно.
- Системный шрифт только внедряется через callback: в прошивке ещё неизвестно, где находится реальный рендерер глифов.
- Пока нет ни испытания на Defender, ни нового безопасного загрузочного слота, ни образа для прошивки.
