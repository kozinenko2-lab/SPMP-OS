# Состояние аппаратного HAL после Stage 15

## Реализовано и проверено в коде

- Преобразование исходных масок `emuIfKeyGetInput` → нормализованные кнопки; `Power` по умолчанию не присвоен.
- Промежуточный адаптер эмуляторного API штатной eCos: `spmp_legacy_input_init` принимает указатели на функции и маппинг `emuIfKeyInit` конкретного устройства. Прямых догадок об адресах функций нет.
- Абстрактный видеовывод 16-бит RGB565 и обратные вызовы звука, клавиш и часов через проверяемую `spmp_hw_adapter`.
- Валидация карты RAM: пять областей (OS, core, game, video, audio) и резерв загрузчика проверяются на перекрытия и арифметическое переполнение `spmp_hal_check_layout`.
- Логическая интеграция с загрузчиком ELF32 Stage10: данные интерфейса и код ядра учитываются раздельно, гостевой код не исполняется на ПК.
- ARMv5 EABI5 `.o` модули собраны для UI, декодирования кнопок, промежуточного HAL и проверок памяти.

## Что ещё блокирует запуск на физическом Defender

1. Получение **реальной** карты RAM, размеров и резервов RedBoot. `0x80000000` из tests/ui/layout_harness.c **ИСКУССТВЕННЫЙ** адрес, не использовать на плате.
2. Путь штатного запуска в пользовательской RAM и таблица системных импортов eCos или независимый native HAL.
3. Реальные видеодрайвер LCD, аудио PCM, работа с FAT и показ оверлея на устройство.
4. UART-логгер для записи событий в диагностический файл с периодической синхронизацией.
5. Подтверждение Power GPIO/PMIC (особенно если кнопка обрабатывается в загрузчике или выключает устройство аппаратно).
6. Согласование D-cache/I-cache после загрузки ARM ELF-кода и проверки защищённого перехода на entry point.
7. Реальная многократная смена ROM/ядер, тестирование отключения питания на записи сохранения и измерение RAM.

**Никаких записей во Flash, RedBoot или оригинальный FSP не выполнялось.**
