# Результаты DefenderOS Stage 1

Дата исследования: 2026-11-11.

## Реально выполнено

* Прочитаны предоставленные пользователем `Images_RedBoot_201000427.img` и `/IMAGE/8000_MMI.RAP` из `mmm-firmware-v3_FSP.img`.
* Проверено ровно 5 вариантов PRAW; у всех вложенный ARM ELF e_entry равен `0x00030040`.
* Структура набора сегментов ELF в вариантах 1/2/4 совпадает между собой; для 3/5 совпадает и отличается от первой группы. Нет оснований считать сегменты местом для собственного кода.
* Подтверждены ASCII-маркеры механизмов RedBoot `linux_kernel.rap`, `bootcfg`, `bootkernel`, `go_with_addr` и `RedBoot>`. Их доступность на Defender через UART неизвестна.
* В оригинальном MMI подтверждены `fatfs_mkdir`, `fatfs_rename`, `fatfs_rmdir`, `fatfs_unlink` и три пути `/fat20a0`, `/fat20a1`, `/fat20a2`.
* Написан рабочий C прототип файлового браузера, рисующий собственный 320×240 RGB565 интерфейс. На компьютере используется read-only POSIX FS backend.
* ARMv5TE в виде relocatable ELF32: `ram_probe_armv5.o`, `safety_pattern_armv5.o`. Оба объекта проверены `readelf` и `llvm-objdump`.
* Автоматические тесты моделей навигации и RGB565 PPM-экспорта завершились успешно (2 из 2).

## Чего нет

Нет проверенной загрузки на Defender, нет самостоятельного ядра со стартовым ARM-кодом, UART-порта, подтверждённой DRAM-карты, драйвера NAND/SD/LCD/audio, компиляции в поддерживаемый `.RAP`, работающего Dual Boot и портированного Linux. Поэтому **не существует готового к записи образа DefenderOS**.

## Ближайший критический путь

(1) Установить реальный Boot Bridge и RAM map — (2) реализовать eCos/HAL — (3) запустить собственное меню на устройстве — (4) исследовать независимый RAM boot — (5) только после проверки аппаратного восстановления обсуждать постоянную альтернативную загрузку.
